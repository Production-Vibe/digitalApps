# AGENTS.md — Контракт работы над «ЦифровойНаряд»

Этот файл — обязательный контекст для любой работы с репозиторием. Читать перед
началом. Порядок приоритета: этот файл → `docs/specs/*.md` → код-модули
`modules/*.md`.

**При старте нового диалога (подхват контекста) обязательно:**
1) прочитать `docs/reports/STATUS.md` — живое состояние (последний этап, открытые
   баги, следующий шаг, активный URL деплоя);
2) при необходимости — датированный отчёт по ссылке из STATUS.md;
3) `docs/МАСТЕР-ДИАГНОСТИКА.md` — при жалобах на «Загрузка…»/пустую страницу.

## Что это за проект

«ЦифровойНаряд» — система управления производством подъёмных агрегатов (ПА),
работающая поверх **Google Таблиц + Google Apps Script WebApp**:

- Excel (VBA) → выгрузка номенклатуры в лист `Catalog`
- Google Таблицы — единственное хранилище данных (12 листов)
- Google Apps Script — веб-интерфейсы ролей + серверная логика

Цель: заменить бумажные наряды цифровым потоком
«планирование запусков → выдача нарядов нач. смены → выполнение оператором →
контроль ОТК» до полной готовности партии.

## Общая концепция (полный контекст агента)

### Зачем нужен проект
Бумажные наряды: теряются, медленные, нет прозрачности — начальник смены и
ОТК не видят реального статуса выполнения. Система делает процесс полностью
цифровым и прослеживаемым до готовности партии.

### Полный поток (end-to-end)
```
Планирование запусков (master)
  → Выдача нарядов нач. смены (shift)
  → Выполнение оператором (operator)
  → Контроль ОТК (otk)
```
до полной готовности партии.

### Стек и особенность
- **Excel (VBA)** → выгрузка номенклатуры в лист `Catalog`.
- **Google Таблицы** — единственное хранилище данных (12 листов), БЕЗ отдельной БД.
- **Google Apps Script WebApp** — серверная логика + веб-интерфейсы ролей.
- Бесплатный стек Google, без отдельного сервера/БД/фронтенд-фреймворка.

### Роли и страницы
- **master** (нач. цеха): дерево номенклатуры, запуски на ПА, Dashboard, печать — `?page=master-app`.
- **shift** (нач. смены): выдача нарядов операторам из запусков (станок, кол-во) — `?page=shift-app`.
- **operator**: открывает смену на станке, принимает наряды, вводит тех. переходы — `?page=operator`.
- **otk**: приёмка/брак/закрытие нарядов, возврат на доработку — `?page=otk-app` (полная страница).

### Данные и модули
- **12 листов**: `Catalog`, `Planning`, `Launches`, `Queue`, `WorkOrders`, `Shifts`,
  `PrintQueue`, `Сотрудники`, `Equipment`, `Наряды`, `Переходы`, `Закрытые`.
- **13 модулей Apps Script**: `Code`, `Config`, `Auth`, `MasterUI`, `ShiftUI`,
  `PlanningAPI`, `CatalogAPI`, `Launches`, `OperatorUI`, `OtkUI`, `Shifts`, `NaryadAPI`, `PrintQueue`.

### Жизненный цикл наряда / статусы
- Наряд: `created → in_progress → waiting_otk → closed`, а также `rework` («Доработка»):
  ОТК возвращает наряд оператору → `rework` → оператор правит → снова `waiting_otk` → `closed`.
- Запуск: `К запуску → Выдано → Готово`.

### Ключевые особенности
- Чтение листов по именам колонок (`headers.indexOf`) — устойчиво к смене порядка.
- Событийная модель: `onEdit` (Planning → Queue → WorkOrders) + `doPost` для VBA.
- Деплой **только ручной** (без clasp): правка `.md` → `check-modules.js` →
  копирование в редактор Apps Script → «Новая версия».
- `modules/*.md` = дословные `.gs`-исходники (исполняемый JS, не документация).
- MasterUI/ShiftUI — полные страницы; OperatorUI — фрагмент + `runInsertedScripts`.

- **Следующий этап**: см. актуальный `docs/reports/STATUS.md` (живое состояние —

## Источник правды

**Файлы `modules/*.md` — это дословные `.gs`-исходники, а НЕ документация.**
Каждый код-модуль `.md` 1:1 маппится в `.gs`-файл модуля Apps Script с тем же
именем. **Весь файл целиком — это рабочий JS-код** (в `modules/*.md` нет
markdown-обёрток/заголовков, которые нужно было бы отрезать).

Код-модули (деплоятся, в `modules/`): `Code`, `Config`, `Auth`, `MasterUI`,
`ShiftUI`, `PlanningAPI`, `CatalogAPI`, `Launches`, `OperatorUI`, `OtkUI`,
`Shifts`, `NaryadAPI`, `PrintQueue`.

Документы (НЕ деплоятся): `README.md`, `AGENTS.md` (в корне);
`Мастер-промпт.md`, `МАСТЕР-ДИАГНОСТИКА.md`,
`чек-лист внедрения - цифровые наряды, статусы.md` (в `docs/`).

## Роли системы

Роли хранятся в листе `Сотрудники`: колонки `login | password | ФИО | role`.

| role | Интерфейс | Страница |
|---|---|---|
| `master` | Начальник цеха: дерево номенклатуры, запуски на ПА, Dashboard, очередь печати | `?page=master-app` (полная страница) |
| `shift` | Начальник смены: выдача нарядов операторам из запусков | `?page=shift-app` (полная страница) |
| `operator` | Оператор: смены, назначенные наряды, тех. переходы | `?page=operator` (фрагмент) |
| `otk` | ОТК: приёмка/брак/закрытие нарядов, возврат на доработку | `?page=otk-app` (полная страница) |

Роутинг: `doGet` в `modules/Auth.md` по параметру `page`. После логина роль
`shift` направляется на `shift-app`, `otk` — на `otk-app`, остальные (кроме
`operator`) — на `master-app`. Детально — `docs/specs/roles.md`.

## Деплой (только ручной!)

**Никакого clasp.** Никаких скриптов исключения из пути.

1. Изменить `modules/*.md` (весь файл — это тело).
2. Проверить синтаксис (см. «Верификация кода»).
3. Скопировать **весь файл целиком** в редактор Apps Script (файл с тем же
   именем) на таблице, чей scriptId указан в `docs/МАСТЕР-ДИАГНОСТИКА.md`
   (ШАГ 2), и сменить версию активного `/exec` на «Новая версия».
4. Не деплоить без явного согласия пользователя и без предупреждения, что
   меняется. По завершении этапа деплоя сообщать пользователю **«тестируй»**.

Полная пошаговая процедура —
`.opencode/skills/digitalapps-deploy/references/deploy-procedure.md`;
почему деплой ручной, без clasp — `docs/specs/adr/deploy-manual.md`.

## Верификация кода

- Каждый изменённый код-модуль должен проходить синтаксическую проверку.
- Прогон:
  `node .opencode/skills/digitalapps-deploy/scripts/check-modules.js`
  (без аргументов — все модули; с именами — выбранные). Скрипт берёт файл
  целиком, гоняет `node --check` через временный файл, а для UI-модулей
  дополнительно проверяет `<script>...</script>` отдельно. Код выхода: `0` — всё
  OK, `1` — синтаксис сломан, `2` — модуль не найден.
- PowerShell: `cmd1; if ($?) { cmd2 }` (без `&&`).
- Файлы-модули должны оставаться самодостаточным JS (без JSX/TS): они
  исполняются движком Rhino/V8 в Apps Script (ES5/ES6+ совместимо).

## Технические конвенции кода-модулей

Только правила, которых нет в `docs/specs/architecture.md` (полные страницы vs
фрагменты, навигация через `appBaseUrl()`, чтение листов по именам колонок
`headers.indexOf` — см. там):

- В серверных template-литералах НЕ использовать `\'` (только `'`).
- ⚠️ `check-modules.js` НЕ отлавливает `\'` в inline-`<script>` UI-модулей
  (он ловит только JS-синтаксис). `\'` в inline-скрипте ломает парсинг в
  `runInsertedScripts` → `SyntaxError: Unexpected string` → «вечная загрузка».
  Поэтому после правки любого UI-модуля (OperatorUI/MasterUI/ShiftUI) вручную
  проверять `grep \\' <модуль>` — должно быть 0 вхождений. Кавычки в
  HTML-атрибутах onclick передавать HTML-сущностями (`&#39;`, `&quot;` — как
  уже используется для `acceptOrder`/`closeShift`), а не `\'`.
- Для `\n` внутри JS-строк (напр. в `JSON.stringify` данных страницы) в `.md`
  писать `\\n`.
- Сложные данные в HTML вставлять через `${JSON.stringify(...)}` + `escapeHtml`.

## Базовый процесс работы

Каждый этап работ выполняется по схеме: **План → Реализация → Проверка →
Отчёт** (см. `docs/reports/` — отчёт пишется по завершении этапа: что сделано,
как проверено, что осталось, следующий шаг).

## Скиллы — обязательный триггер по фазе

Скиллы лежат в `.opencode/skills/`. **Перед началом работы определи фазу задачи и
обязательно загрузи профильный скилл (инструмент `skill`), даже если считаешь,
что справишься без него. Не начинай работу в фазе, пока соответствующий скилл не
загружен.** Скиллы остаются on-demand (их нельзя инъектировать в каждую сессию),
но применение — обязательное правило, а не опция.

| Фаза задачи | Обязательный скилл (загрузить первым) |
|---|---|
| **Планирование / уточнение задачи** | `brainstorming`, затем `writing-plans` |
| **Отладка / расследование бага** | `systematic-debugging` (root cause → гипотеза → тест) |
| **Изменение визуального UI** | `web-design` (усечённо) или `frontend-design` |
| **Написание/изменение логики кода** | профильный скилл по домену; `writing-plans`, если задача многошаговая |
| **Проверка / завершение этапа** | `verification-before-completion`; при деплое также `digitalapps-deploy`; при E2E — `webapp-testing` |
| **Отчёт / docs** | `doc-coauthoring` |

Каждая завершённая работа проходит `verification-before-completion`: доказательства,
а не «предположительно всё ок».

Оговорка по `web-design`: применяем **усечённо** — из него реально используем
`style-seeds.md`, `interaction-patterns.md` (L1), `quality-checklist.md`. Остальное
(DESIGN.md-конвейер, 58 брендов, motion-library, GSAP, скрипты) неприменимо к
нашим Apps Script UI (интерфейсы живут в серверных template-литералах).

## Control plane и проектные subagents

- **`opencode.json`** подключает в каждую сессию ключевые инструкции: `AGENTS.md`,
  `docs/reports/STATUS.md` (живое состояние), `docs/specs/architecture.md`,
  `instructions/safety.md`, `instructions/verification.md`. Правила вынесены в
  `instructions/`, а не зашиты в один `AGENTS.md`.
- **Проектные subagents** (в `.opencode/agents/`), зеркалят повторяемые процедуры:
  - `deploy` — ручной деплой `modules/*.md` в Apps Script (обёртка skill `digitalapps-deploy`);
  - `e2e` — Playwright-прогоны ролей (обёртка `docs/testing/e2e-runbook.md`).
- Бизнес-роли (master/shift/operator/otk) — это роли приложения, а не engineering
  subagents; их логика в `docs/specs/*` и `modules/*`.

## Do / Don't

**Do:**
- Отвечать на русском.
- Сверить с фактическим содержимым `modules/*.md` перед правкой (не полагаться
  только на README/память).
- Фиксировать новые архитектурные решения в `docs/specs/adr/`.
- Коммитить по завершении логического этапа работ (по явному согласию либо в
  рамках согласованного этапа).
- Не забывать `docs/МАСТЕР-ДИАГНОСТИКА.md` при жалобах на «Загрузка…»/пустую
  страницу.

**Don't:**
- НЕ создавать/править `dist/`, `deploy/` — их нет в проекте (clasp устарел).
- НЕ править генерируемые артефакты — их нет, исходник это `.md`.
- НЕ удалять листы/функции, на которые ссылается другой модуль (кросс-ссылки
  глобальны в Apps Script).
- НЕ добавлять комментарии в код, если их не запросили.
- НЕ переименовывать файлы-модули без обновления README + роутинга `doGet`.

## Definition of Done

- Все изменённые модули проходят `scripts/check-modules.js` (exit `0`).
- Изменения синхронны с README (если менялась структура/роли/листы).
- Решения зафиксированы в specs при необходимости.
- **Живое состояние обновлено**: `docs/reports/STATUS.md` актуализирован
  (последний этап, открытые баги, следующий шаг, URL деплоя, коммиты).
- Деплой согласован с пользователем и выполнен вручную (или явно отложен).
- Пользователь предупреждён: «тестируй».
