# Отчёт: Полный E2E-цикл роли ОТК — подтверждение багов и находка по производительности

Дата: 07.09.2026
Этап: ОТК-интерфейс (приёмка/брак/закрытие/доработка нарядов) — полный E2E-прогон
Деплой: `https://script.google.com/macros/s/AKfycbzkYDDqEmavt3QHECKoxyW5AjHlu4C0FtmwATpFAkYCVkv4TT5gjO1JFRgCsr1rzQsdHA/exec`

## 1. Что делали

Прогнали полный E2E-набор роли ОТК (`tests/e2e/test_otk_full.py`) на активном деплое:
фильтрация по вкладкам (A), карточка наряда (B1), «Проверить переход» (B2/BUG-1),
отрисовка агрегатов (K), закрытие позитив (D1), отмена в confirm (D2), закрытие с
браком (D3) и «негативные» сценарии устойчивости (H1–H5, F1/F4/F5), rework-цикл
(E1/E2).

До переполнения данных очереди (см. п. 3) все сценарии исполнялись и дали
детерминированные результаты. В конце прогона, из-за накопленных орфан-сидов
(см. п. 3), очередь ОТК перестала отдавать данные, и дальнейший UI-прогон стал
невозможен — это и есть отдельная находка по производительности.

## 3. Подтверждённые баги

### BUG-1 (HIGH): «Проверить переход» НЕ сохраняет проверку в Transitions
- Кнопка в OTK-UI (`modules/OtkUI.md`, `checkOne`) шлёт `tp=escapeAttr(t.tp)` —
  строку вида `'5'`.
- Google Sheets хранит `№ перехода` числом `5`; сервер `checkTransition`
  (`modules/NaryadAPI.md`) сравнивает `===` → несовпадение → запись НЕ происходит.
- Но сервер возвращает `{status:'checked'}` в любом случае → UI показывает ложный
  toast «проверен», а данные `Принято`/`Брак` и `checkedCount` не обновляются.
- Влияет на: проверку переходов через реальный UI, аккумуляцию агрегатов, любой
  реальный процесс приёмки. **Критичен для работы роли ОТК.**
- Обход в E2E: сид через API с `int(tp)` (`seed_api._tp_int`) — отрисовка агрегатов
  (сценарий K) работает, что доказало: сам UI-рендер корректен, ломался именно
  серверный матчинг.

### H1/H2 (MEDIUM): наряд можно закрыть без единого перехода
- `closeNaryad` не требует наличия переходов и не проверяет наличие проверенных
  (checked). Закрытие created/непроработанного наряда возможно — это противоречит
  процессу (нельзя «закрыть» партию, которую никто не делал и не принимал).

### H3 (MEDIUM): итоги закрытия не согласуются с переходами
- `closeNaryad` пишет итоги из переданных `total_accepted`/`total_defect`, а не
  агрегирует из переходов наряда. При проставлении «Принято 5» и нулевых
  проверенных переходах итоги расходились (переходы 0/0, закрытие 5/0).

### H4 (MEDIUM): молчаливый успех при несуществующем переходе
- `completeTransition`/`checkTransition` возвращают success даже если строка с
  указанным `tp` не найдена — нет флага `found`. Опечатка/потеря перехода не
  обнаруживается.

### H5 (MEDIUM): сервер не валидирует принятое/брак по количеству
- `accepted_qty` может превышать `quantity` наряда (принято 999 при количестве 5) —
  сервер принимает без ошибки.

### Перф-баг (HIGH): очередь ОТК не грузится при большом числе открытых нарядов
- `getOtkQueue` (`modules/OtkUI.md`) для каждого открытого наряда вызывает
  `otkAggregate` → `getTransitions(naryadId)` (`modules/NaryadAPI.md`), который
  каждый раз читает **весь лист Transitions** целиком.
- С ~162 открытыми нарядами (накопленные E2E-орфаны) это O(N×M) чтений превышает
  **жёсткий лимит 30 секунд** Apps Script → RPC `getOtkQueue` тихо застревает,
  очередь ОТК остаётся пустой/вечной «Загрузки».
- Подтверждено прямым RPC: `getNaryady` → 2.3s, `getOtkNaryad` → 3.6s,
  `getOtkQueue` → Timeout 30s+.
- Это реальная проблема масштабирования: при росте числа открытых нарядов
  страница ОТК деградирует. **Нужен однопроходный расчёт агрегатов**
  (один раз прочитать весь Transitions и сгруппировать по наряду).

## 4. Гарнесс/инфраструктурные заметки

- Множественные быстрые `doPost`-сиды приводили к транзиентным 404 от GAS —
  добавлены ретраи (`seed_api.post`).
- Повторная навигация на один и тот же GAS-URL могла не перезагрузить iframe
  (скрытая `#queueTable`) — `open_otk` теперь ждёт именно наполненного
  содержимого, а не факта существования div.
- **Главный ограничитель прогона — накопление орфан-нарядов** (нет API-действия
  удаления/пак-закрытия). До очистки данных дальнейший UI-прогон ОТК невозможен.

## 5. Рекомендации / следующий шаг

1. **Зачистка тестовых данных E2E** в `WorkOrders`/`Transitions`/`ClosedOrders`
   (вручную или скриптом на таблице) — разблокирует очередь и дальнейшие прогоны.
2. **Точечный фикс BUG-1 (HIGH)**: в `checkTransition`/`completeTransition`
   нормализовать `tp` в число (`Number(data.tp)`) перед сравнением; заодно рендерить
   `tp` в `checkOne` числом.
3. **Перф-фикс `getOtkQueue`**: один проход по Transitions с группировкой по
   наряду вместо O(N×M) чтений.
4. **Валидации**: H1/H2 (требовать переходы/проверенные перед закрытием), H3
   (агрегировать итоги из переходов), H4 (флаг `found`), H5 (limits по quantity).
5. Обновить `docs/reports/STATUS.md` и закоммитить этап по согласию.
