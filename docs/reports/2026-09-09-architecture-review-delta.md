## C. Живые риски (актуальны после сверки)

### C1. VBA-консолидация — единственный реальный остаток «двух учёта»
В коде канон сведён к WorkOrders (ADR-003), кириллические листы выведены. Реальный остаточный риск — VBA-клиенты, исторически писавшие в кириллические листы; часть переведена на новые листы, полный переезд VBA — отдельным этапом (TODO STATUS).

### C2. Трассировка «git-commit ↔ версия /exec»
Манифест деплоя есть (ADR-004, v32/v33/v34), но связка «какой commit на какой номер версии Apps Script выкачен» заполняется вручную и местами «?». Самое дешёвое надёжностное улучшение: замыкать строку манифеста в момент «Новая версия» (commit + чистота дерева + номер версии).

### C3. Семантика частичной выдачи («К запуску» vs «Выдано»)
Статус Launches «Выдано» (полная выдача) vs «К запуску» (остаток) — фильтр/статус хрупкий. Предложение: выводить статус по данным (выданное количество из Queue/WorkOrders), а не хранить.

### C4. Граница «когда мигрировать с Sheets»
Определить заранее критерии перероста (число нарядов/месяц, одновременные пользователи, время отклика Dashboard), а не решать в момент боли. Конкурентная запись из разных смен одновременно — первый сигнал.

### C5. Модель безопасности
Роль в URL/имя/наряд + пароли открытым текстом + доступ по настройке развёртывания. QR-доступ оператора (`?page=operator&name=..&id=..`) уже есть — «закрытость» инфраструктуры размывается. До публичного/внешнего доступа — заложить простой токен-слой (HMAC от login+role+salt) или карточную/QR-идентификацию.

### C6. Dashboard-отображение rework в Master/Planning
Открытый вопрос ADR-005 (как показывать наряд-«Доработка» на Dashboard нач. цеха). Визуальный, кодовый канон уже несёт `rework`.

## F. Предложение «на обсуждение» (не решение): канонический объект-факт партии/наряда

Текущее состояние: канон наряда — `WorkOrders`; итоги закрытия пишутся в `ClosedOrders`
повторной записью (`closeNaryad.appendRow`), а `getClosingInfo` читает их оттуда. Это
**две записи одного факта** (статус+переходы в WorkOrders/Transitions, принято/брак в
ClosedOrders). Пока согласованы через один RPC-флоу, расхождения маловероятны, но они
не гарантированы.

Для размышления (зафиксировать отдельным ADR при необходимости):
- Определить канонический объект-факт (наряд/партия) и единственный «ведущий» лист.
- `ClosedOrders` рассматривать как **производную проекцию (materialized view) итогов**, пересчитываемую по WorkOrders+Transitions при закрытии, а не как независимый источник.
- Гарантировать консистентность `accepted/defect` между переходами (Transitions) и итогами (ClosedOrders) единой функцией закрытия (сейчас частично покрыто guard'ами H1/H5 v32).

> Это рекомендация/вопрос для обсуждения, не принятый ADR — требует отдельного
> решения, если будете двигаться в эту сторону.
