# Отчёт: Устранение флейка B1 в E2E-харнесе (гонка отрисовки карточки наряда)

Дата: 09.09.2026
Этап: стабилизация E2E-харнесса роли ОТК (без изменений модулей, без деплоя)
Деплой: не требовался
Родительский этап: фиксы перф v33+v34 (`docs/reports/2026-09-09-otk-perf-v33-v34.md`).

## 1. Проблема

В первом прогоне `ND_SKIP_E2=1` на v34 падали все 3 проверки сценария B1
(«карточка наряда»): проверки «деталь/код/кол-во/статус», «Решение ОТК»+кнопок и
«таблица 2 перехода» давали ложный FAIL для наряда Н-260909-666376. При этом тот же
наряд далее проходил свои же сценарии B2 и D1 — карточка открывалась и
взаимодействовала корректно. Повтор прогона — чистый 27/27. Флейк, а не регресс.

## 2. Root cause (по коду + evidence)

- `OtkUI.openNaryad(id)`: сразу присваивает `#naryadCard.innerHTML` = плейсхолдер
  «Загрузка наряда…», **затем** асинхронно вызывает `getOtkNaryad(id)`; полная
  карточка появляется одним `innerHTML =` в `renderNaryadCard()`. Значит элемент
  `#naryadCard` существует с момента клика (до загрузки данных).
- Харнесс `otk_open_card()` ждал mere-`#naryadCard` через
  `wait_for_in_any_frame` → резолвился мгновенно на плейсхолдере, а не на рендере.
- `card_text()` затем опрашивал текст с условием «нет „Загрузка" и есть „Наряд "»,
  но с жёстким окном **6s**.
- B1 — первое открытие карточки на свежей странице: сразу после `getOtkQueue`
  выполняется холодный `getOtkNaryad`; при разбросе латентности GAS он изредка
  превышает 6s → `card_text` возвращает `""` → все 3 проверки B1 падают.

Вывод: приложение корректно (карточка рендерится, просто позже), флейк — в бюджете
ожидания харнесса. Тот же класс уязвимости был в H1 (только `#naryadCard` + 6s).

## 3. Изменения (только `tests/e2e/`)

- **`flows.py` — `otk_open_card()`**: вместо mere-`#naryadCard` ждёт **отрисованную**
  карточку — во фреймах опрашивается `#naryadCard`, пока текст не перестанет
  содержать «Загрузка» и не будет содержать «Наряд » (бюджет 20s); возвращается
  фрейм карточки. При зависании RPC — явный TimeoutError, а не тихий `""`. Покрывает
  сразу все вызовы: B1/K/D1/D2/D3/H2/F1/F4/F5/E1.
- **`test_otk_full.py` — `card_text()`**: дефолт окна 6s → 15s (защита H1).
- **`test_otk_full.py` — A-чеки**: оба `wait_tab_rows` переведены с 15s на 30s
  (как бюджет `open_otk`) — тот же класс проблемы: наполнение `#queueTable` на
  свежей странице при большой очереди/нагрузке GAS может превышать 15s
  (наблюдалось в 1 из 5 запусков B1-цикла).
- **`test_otk_full.py` — `ND_SCENARIOS`-фильтр**: env-строка с именами сценариев
  (`ND_SCENARIOS="B1: карточка наряда"`) — запуск одного/нескольких сценариев;
  комбинируется с `ND_SKIP_E2`/`ND_ONLY_E2`. Нужен для дешёвого повтора
  конкретного сценария (малый расход дневной квоты GAS).

## 4. Проверка (v34, активный /exec)

| Прогон | Итог |
|---|---|
| `ND_SCENARIOS="B1: карточка наряда"` ×5 | **5/5 в каждом из 5 запусков** (целевой флейк не воспроизводится) |
| `ND_SKIP_E2=1` (полный регресс) | **27/27** — покрывает все вызывающие `otk_open_card` сценарии, включая E1 |

`py_compile` изменённых файлов — OK. `ND_ONLY_E2` не перегонялся: сценарий E2 не
использует `otk_open_card`/`card_text` — регресс от правок полностью покрыт
`ND_SKIP_E2`.

## 5. Вывод

Флейк носил системный характер ожидания харнесса, а не дефекта приложения.
Правки устраняют и B1, и смежный риск A-чеков/H1 одним паттерном: ожидание
**условия отрисовки** с бюджетом, согласованным с реальной латентностью первого
холодного RPC GAS.
