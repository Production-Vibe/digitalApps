# Отчёт: Перепроверка v32 после сброса квоты → НЕ квота, а перф per-row sheetHeaders: деплой v33+v34, полный зелёный E2E

Дата: 09.09.2026
Этап: устранение производительностной деградации списков (очередь ОТК и оператор)
Деплой: v34 — `https://script.google.com/macros/s/AKfycbwEW0eGDTYTuBStMJ7nc8cXOF3OzQ1YC9cT4t-Avmaqy4I1HuuzfQ0lnrwa0wtu8Wxj5g/exec` (v33 промежуточный — см. ниже)
Родительский отчёт: `docs/reports/2026-09-08-otk-fixes-deploy.md` (открытый пункт «перепроверка после сброса квоты»).

## 1. Что делали

После сброса суточной квоты GAS (~10:00 МСК) повторили прогон на v32 — очередь ОТК
по-прежнему отвечала 57–88s, т.е. подозрение на throttling квоты не подтвердилось:
диагностика показала, что виноват не GAS-лимит, а код. Найден общий перф-паттерн —
row-conversion-функции читали заголовки листа на каждую строку. Устранён двумя
деплоями (v33 — очередь ОТК, v34 — глобально через мемо-кеш заголовков). Итог —
полный зелёный E2E на v34.

## 2. Диагностика (на v32, после сброса квоты)

| RPC | Время | Комментарий |
|---|---|---|
| `getOtkNaryad` | 3–4s | норма |
| `getNaryady` (224 строки) | 2.3s | норма |
| `getOtkQueue` | 57.2s / 88.2s | патология — очередь ОТК «вечная загрузка» |
| `getOperatorInWork` (187) | 40.8s | патология — операторский список |
| `getOperatorClosed` (27) | 52.7s | патология |

Consent-гейт приложения открывался корректно (рендер страницы проходил), сессионные
проблемы исключены. Root cause — в `naryadRowToObject`/`transitionRowToObject`
(`NaryadAPI.md`), которые вызывают живую `sheetHeaders()` (`getRange().getValues()`)
на **каждую** строку списка → сотни повторных чтений заголовков листа за один RPC.
`getOtkQueue` (v32) дополнительно звал row-конвертеры через `getOtkNaryad`-подобные
пути, усугубляя картину.

## 3. Внесённые изменения

### v33 — `modules/OtkUI.md` (перф только очереди ОТК)

`getOtkQueue`/`transitionAggregates` переписаны: индексы колонок берутся **один раз**
перед циклом, строки обрабатываются прямым индексированием (без per-row
`sheetHeaders()`). Сигнатуры не менялись.

### v34 — `modules/NaryadAPI.md` (перф глобально, все роли)

`sheetHeaders()` мемоизирована на время одного исполнения: кеш по `sheet.getSheetId()`
(глобал `_sheetHeadersCache`). Заголовки листа в рамках одного RPC не меняются,
поэтому кеш безопасен; глобалы в Apps Script сбрасываются на каждом исполнении.
Функции-конвертеры и все их потребители (оператор, ОТК, смены, мастер) ускоряются
без изменения сигнатур и без риска расхождений данных.

Синтаксис проверен: `node .opencode/skills/digitalapps-deploy/scripts/check-modules.js NaryadAPI` → PASS; `\'` → 0.

## 6. Выводы

- Подозрение на throttling квоты GAS **не подтвердилось**: реальная причина
  деградации — алгоритмическая (per-row чтение заголовков). После фиксов RPC
  отдают списки за секунды при том же объёме данных (224 открытых наряда).
- Перф паттерн устранён **глобально** одним модулем (`NaryadAPI`): оператор, ОТК,
  смены, мастер получают ускорение без дальнейших точечных правок.
- E2E-зелень подтверждена двумя независимыми прогонами; разовый B1-флейк —
  тайминг харнесса, не логика.
