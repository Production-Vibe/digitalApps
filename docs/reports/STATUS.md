## Последний завершённый этап

- **09.09.2026 — Устранён флейк B1 в E2E-харнесе (гонка отрисовки карточки) +
  укреплены A-чеки; деплой не требовался.** Root cause: `otk_open_card()` ждал
  mere-появление `#naryadCard` (плейсхолдер «Загрузка наряда…» ставится до RPC), а
  первый холодный `getOtkNaryad` под нагрузкой GAS может превышать 6s-окно
  `card_text` → пустой текст карточки → ложные FAIL B1 (тот же наряд проходил B2/D1).
  Фикс (только `tests/e2e/`): `otk_open_card()` ждёт **отрисованную** карточку
  (20s), `card_text` 6s→15s, добавлен `ND_SCENARIOS`-фильтр (дешёвый повтор
  сценария), A-чеки на бюджете 30s (как `open_otk`). Проверка на v34:
  `ND_SCENARIOS="B1: карточка наряда"` ×5 — 5/5 во всех запусках; `ND_SKIP_E2`
  — **27/27** (регресс покрывает все вызовы `otk_open_card`, включая E1).
  Отчёт: `docs/reports/2026-09-09-harness-b1-flake.md`.
- **09.09.2026 — Перепроверка v32 после сброса квоты выявила НЕ квоту, а перф:
  per-row `sheetHeaders()` → деплой v33+v34, полный зелёный E2E.** После сброса
  суточной квоты GAS (~10:00 МСК) очередь ОТК всё равно отвечала 57–88s (v32).
  Diagnostics: `getOtkNaryad` 3–4s, `getNaryady` 2.3s — квота ни при чём. Root cause:
  row-conversion-функции (`naryadRowToObject`/`transitionRowToObject`) вызывают живой
  `sheetHeaders()` (getRange+getValues) на КАЖДУЮ строку списков → сотни чтений
  заголовков. **Деплой v33** (`OtkUI.md`): `getOtkQueue`/`transitionAggregates` —
  индексы колонок один раз, прямое индексирование; очередь **57–88s → 2.5–3.8s**,
  `ND_SKIP_E2` 27/27. **Деплой v34** (`NaryadAPI.md`): мемоизация `sheetHeaders()`
  (кеш по `sheetId` на время исполнения) чинит глобально и оператора:
  `getOperatorInWork` 40.8s→**3.1s**, `getOperatorClosed` 52.7s→**3.6s**; списки
  Master/Shift тоже ускоряются. Прогоны на v34: **`ND_ONLY_E2` 16/16** (полный
  rework-цикл: выдача→оператор→переход→ОТК→доработка→фикс→закрытие 1/1),
  **`ND_SKIP_E2` 27/27** (первый прогон 24/27 — B1 разовая гонка отрисовки карточки,
  тот же наряд прошёл B2/D1; повтор 27/27). Сид-запуски «К запуску» создавались для
  E2 через `createLaunch` (остаток запусков в проде кончился). Отчёт:
  `docs/reports/2026-09-09-otk-perf-v33-v34.md`.
- **08.09.2026 — Фиксы роли ОТК (BUG-1, H1–H5, перф) задеплоены (v32) + усилен
  E2E-харнесс.** Реализованы и задеплоены вручную (версия 32): `Number(tp)` и флаг
  `found` в check/completeTransition (BUG-1, H4), валидация H5 (accepted≤quantity),
  guard в `closeNaryad` (H1/H2: нельзя закрыть без проверенных переходов), однопроходная
  `transitionAggregates()` в `getOtkQueue` (перф: O(N+M) вместо O(N×M); очередь грузится
  при 150+ открытых нарядах). Харнесс: точные toasts/`close_outcome`, `wait_queue_table`,
  data-fallback оператора, фикс needle «Ждёт ОТК», F4/F5 доведены. Прогоны на v32:
  стабильно PASS A/B1/B2(+BUG-1 реальная запись)/K/D1/D2/D3/H1/H2/H3/H5/F1/F3/F4/F5/E1,
  E2 изолированно 14/16 (обе «неудачи» — ложная детекция, устранены). Остаётся
  **throttling GAS** (суточная квота времени выполнения почти исчерпана за день
  прогонов): случайные замирания `getOtkQueue` → 1 сценарий/прогон отваливается —
  не баг логики (`getOtkQueue` однопроходный). Следующий шаг: после сброса квоты
  ~10:00 МСК повторить ND_SKIP_E2 + ND_ONLY_E2 до зелёного и закоммитить.
  Отчёт: `docs/reports/2026-09-08-otk-fixes-deploy.md`.
- **07.09.2026 — Полный E2E-цикл роли ОТК: подтверждены баги + находка по
  производительности.** Прогнан `tests/e2e/test_otk_full.py` на активном деплое.
  Подтверждены: **BUG-1 (HIGH)** — «Проверить переход» не пишет в Transitions
  (`tp` строкой `'5'` vs числом `5`, `===` → ложный toast «проверен»); H1/H2 —
  наряд закрывается без переходов; H3 — итоги закрытия не агрегируются из
  переходов (0/0 vs 5/0); H4 — молчаливый успех при несуществующем `tp`; H5 —
  сервер принимает accepted > quantity. PASS: A, B1, B2-toast, K (агрегаты через
  API), D1/D2/D3, F1/F4/F5, E1 (rework-direct-close). **Перф-баг (HIGH)**:
  `getOtkQueue` — O(N×M) чтений Transitions на каждый наряд; при ~162 открытых
  нарядах RPC превышает 30s-лимит → очередь ОТК вечно пустая/«Загрузка»
  (подтверждено прямыми RPC: getNaryady 2.3s, getOtkNaryad 3.6s, getOtkQueue 30s+).
  Отчёт: `docs/reports/2026-09-07-otk-full-cycle.md`. **Блокер следующего
  UI-прогона: зачистка орфан-сидов E2E в WorkOrders/Transitions.**
- **07.09.2026 — Полный E2E-бизнес-цикл PASS (24/24) на новом деплое англоязычных листов.**
  `tests/e2e/test_bizcycle.py` прогнан на активном `/exec`
  (`AKfycbzkYDDqEmavt3QHECKoxyW5AjHlu4C0FtmwATpFAkYCVkv4TT5gjO1JFRgCsr1rzQsdHA`),

## Закрытые баги

- ✅ **Перф списков всех ролей (HIGH): per-row `sheetHeaders()`** — row-conversion
  (`naryadRowToObject`/`transitionRowToObject`) читали заголовки листа на КАЖДУЮ
  строку → `getOtkQueue` 57–88s, `getOperatorInWork` 40.8s, `getOperatorClosed`
  52.7s. Устранено двустворочно: v33 (`OtkUI`) — прямые индексы в
  `getOtkQueue`/`transitionAggregates`; v34 (`NaryadAPI`) — мемо-кеш `sheetHeaders()`
  по `sheetId` на время исполнения (глобально). Замеры после деплоя:
  очередь 2.5–3.8s, оператор 3.1s/3.6s.
- ✅ **BUG-1 (HIGH) «Проверить переход» не сохранял в Transitions** — `tp` строкой
  `'5'` vs числом; `Number(tp)` в check/completeTransition. Подтверждено реальной
  записью `checked` в E2E (B2). Задеплоено v32 (08.09).
- ✅ **Перф `getOtkQueue` (HIGH)** — O(N×M) чтений Transitions → 30s+ лимит → пустая
  очередь при ~162 нарядах. Заменён на однопроходную `transitionAggregates()` (O(N+M)).
  Задеплоено v32 (08.09); очередь отдаётся при 150+ открытых нарядов.
- ✅ **H1/H2** — `closeNaryad` блокирует закрытие без проверенных переходов
  (guard + toast-ошибка; исключение — direct close из `rework`). v32.
- ✅ **H3** — итоги закрытия согласованы с переходами (проверка 5/0 vs 5/0). v32.
- ✅ **H4** — check/complete возвращают `{error: 'Переход … не найден'}` на
  несуществующий `tp` (флаг `found`). v32.
- ✅ **H5** — сервер отклоняет `accepted+defect > quantity` наряда. v32.
- ✅ **«Пустая OTK-очередь» (рассинхрон `waiting_otk`)** — оператор видел статус
  «Ждёт ОТК», но очередь ОТК не показывала наряд: `getOtkQueue` строил очередь из
  листа `Наряды`, куда shift-поток (WorkOrders) не писал. Устранён переводом
  канона на `WorkOrders` (ADR-003, реализован 07.09).
- ✅ **Баг №1 — переавторизация оператора при F5** (после входа URL оставался `?page=login`).
  Причина: оператор единственный логинился через фрагмент-инъекцию без смены URL.
  Фикс: `modules/Auth.md` — редирект на полную `?page=operator&name=...&id=...`.
  Коммит `5022dc9` (тег `v0.2-e2e`). Подтверждено E2E (F5 не возвращает форму входа).
- ✅ **Баг shift-выдачи** (`loadOperators()` обрывалась без вызова серверной функции) — исправлен раньше, отчёт `docs/reports/2026-09-02-shift-role-testing.md`.
