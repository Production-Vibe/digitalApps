# ADR-003: Единый источник истины для цифрового наряда (WorkOrders ↔ Наряды)

**Статус:** Принято (2026-09-07, вариант A — `WorkOrders` = канон, `Наряды`/`Переходы`/`Закрытые` = учётная проекция).
**Дата:** 2026-09-07.

## Контекст

В системе существуют **два параллельных представления одного домена «наряд»**,
которые пишутся разными путями и не связаны друг с другом по номеру:

1. **`WorkOrders`** — «цифровой» поток, создаётся нач. смены
   (`ShiftUI.issueWorkOrder`, `modules/ShiftUI.md:77`) или из очереди
   (`PlanningAPI.createWorkOrderFromQueue`, триггер `Queue → WorkOrder`
   в `modules/Code.md:77-86`). Колонки по `docs/specs/data-model.md`:
   `Номер | Код детали | … | Оператор | Станок | Кол-во | Статус | Launch ID`.
   Статусы: `created → in_progress → waiting_otk → closed`.
   (`Launch ID` — `ID` запуска из листа `Launches` (`ЗП-yyMMdd-HHmmss`),
   `docs/specs/data-model.md`; у `WorkOrders` есть отсылка к запуску, у
   `Наряды` её нет.)
2. **`Наряды`** — «учётная» система, заполняется оператором через переходы
   (`Переходы`), закрывается ОТК. Создаётся `createNaryad` (`modules/NaryadAPI.md:510`)
   обычно через VBA (`Code.doPost`, `action='create_naryad'`). Статусы:
   `created / in_progress / waiting_otk / rework / closed`. Итоги закрытия —
   отдельный лист `Закрытые` (`closeNaryad`, `modules/NaryadAPI.md:620`).

Оба потока генерируют номера нарядов вида `Н-yyMMdd-HHmm(ss)`, но **не
сверяются и не ссылаются друг на друга**: `WorkOrders` знает `Launch ID`,
`Наряды` связывается только через `Переходы.Наряд`.

### Доказанный разрыв (проверено по коду)

- `NaryadAPI.acceptWorkOrder` (`modules/NaryadAPI.md:305`) принимает задачу
  оператора: ставит `in_progress` в `WorkOrders` и обновляет статус в `Planning`,
  но **НЕ создаёт запись в `Наряды`**.
- После «Принять в работу» оператор видит `loadInWork()` (`OperatorUI.md:579`),
  однако `loadCurrentNaryad`/`getNaryadForOperator` читают **только лист `Наряды`**
  (`NaryadAPI.md:229`). Если строки в `Наряды` нет — оператор не может ввести
  тех. переходы по принятому WorkOrder.
- ОТК-интерфейс (`OtkUI.md`) также работает только с `Наряды`
  (`getNaryady()` → `naryadRowToObject`); задачи из `WorkOrders` он не видит.
- Каждая из систем живёт своей статусной моделью; `rework` существует только
  в `Наряды` (см. ADR-005).

**Следствие:** наряд, выданный через цифровой поток (shift → operator), «зависает»
в `WorkOrders` без продолжения в `Наряды`; либо оператор вручную открывает
существующий наряд `Наряды` (созданный VBA), игнорируя `WorkOrders`. Полный
бизнес-цикл через одну точку входа сейчас невозможен без ручной «склейки».

## Решение (принято)

> **Решение принято: вариант A** — `WorkOrders` = канон, `Наряды`/`Переходы`/
> `Закрытые` = учётная проекция. Реализация оформляется отдельным планом.

**Термины (используются ниже):**
- **Канон (канонический источник)** — единственное место, где факт пишется
  «впервые» и считается истиной; остальные листы — производные.
- **Проекция / материализованное представление** — производный лист, который
  пересчитывается из канона (не пишется бизнес-логикой напрямую).
- **`Launch ID`** — `ID` запуска (`ЗП-yyMMdd-HHmmss`, лист `Launches`), по нему
  `WorkOrders` ссылается на запуск; `Наряды` такой ссылки не имеют.

### Вариант A (рекомендуемый): `WorkOrders` становится каноническим «нарядом», `Наряды`/`Переходы`/`Закрытые` остаются учётной проекцией

- **Канон:** цифровой наряд = строка `WorkOrders` (Launch ID, код, оператор,
  станок, кол-во, статус). Все переходы привязаны к `Номер` из `WorkOrders`.
- **Единый write-path:** при `acceptWorkOrder` оператор вводит тех. переходы
  **напрямую в лист `Переходы` с `Наряд = Номер WorkOrders`** (одна точка записи
  переходов). Лист `Наряды` **пересчитывается** (не пишется логикой): строка
  формируется из `WorkOrders` + `Переходы` как учётная проекция для VBA/печати.
- **Судьба VBA-записей (`doPost.action='create_naryad'`):** при переходе на канон
  VBA **перестаёт быть единственной точкой создания нарядов**. На время миграции
  `createNaryad` (VBA) остаётся, но помечается как legacy и *не должен* создавать
  строки, которые уже есть как `WorkOrders` (или наоборот — создаёт только наряд
  без `WorkOrders`, что фиксируется как исключение для старых сценариев). Финально
  VBA-поток переводится на создание/обновление через `WorkOrders`-канон или
  исключается из записи в `Наряды`.
- `Закрытые` — отчётность после `closeNaryad` (остаётся как есть).
- ОТК и оператор читают из `Наряды` как сейчас (проекция удобна для отображения),
  но источник фактов — `WorkOrders`.
- **Миграция существующих нарядов:** у текущих строк `WorkOrders` и `Наряды`
  **нет общего ключа**. План миграции: сопоставление по составному признаку
  (фИО оператора + код детали + кол-во + дата), де-дупликация, при неоднозначности —
  ручная сверка. Новые наряды заводятся строго через канон, чтобы коллизий номеров
  «`Н-yyMMdd-HHmmss` vs `Н-yyMMdd-HHmm`» не возникало (форматы генерации различаются в
  `issueWorkOrder` и `createWorkOrderFromQueue`).
- **Плюсы:** один источник, полный цикл из одной точки, ОТК и печать работают
  с привычным «нарядом». **Минусы:** требует миграции и аккуратного write-path
  (правило: пишем в `WorkOrders`/`Переходы`, `Наряды` — читают/пересчитывают).

### Вариант B: `Наряды` становится каноном, `WorkOrders` — операционная проекция shift

- Канон — существующая учётная система `Наряды`/`Переходы`/`Закрытые` (не
  ломает VBA и бумажный учёт). При выдаче наряда создаётся сразу строка `Наряды`;
  `WorkOrders` используется только для «входящих задач» shift/operator.
- **Плюсы:** меньше изменений в уже работающем ОТК/VBA; соответствие «бумажному»
  укладу. **Минусы:** цифровой поток продолжает быть «вторым» (риск расхождений
  не исчезает, лишь меняет направление); `Launch ID` и аналитика Dashboard всё
  равно опираются на `WorkOrders`.

### Вариант C: оставить две системы, зафиксировать двусторонний синхронизатор

- Формализовать правила «каждая выдача shift порождает запись в `Наряды`»,
  «закрытие ОТК в `Наряды` обновляет статус `WorkOrders`», с хелпером-мостом.
- **Плюсы:** минимум изменений кода, сохраняются оба представления.
  **Минусы:** не решает корневую проблему (два источника), добавляет хрупкую
  синхронизацию; расхождения будут возникать вновь.

## Последствия (при выборе варианта)

- Для A: доработка `acceptWorkOrder` (переходы в `Переходы.Наряд` по номеру
  `WorkOrders`), пересчёт `Наряды` из канона, разрешение конфликта с VBA-записями
  (`doPost.create_naryad`), согласование миграции существующих нарядов.
- Для B: доработка `issueWorkOrder`/`createWorkOrderFromQueue` (создание сразу в
  `Наряды`), сохранение `WorkOrders` как проекции.
- Во всех случаях: одному номеру наряда — одна строка-источник; переходы всегда
  привязаны к каноническому номеру.

## Взаимосвязь с ADR-005

- ADR-003 принят **независимо от ADR-005** (источник истины не блокируется
  вопросом статуса `rework`).
- ADR-005 принят **вариант C** (общий словарь статусов — независимо); варианты
  A/B — развитие **после** выбора канона по этому ADR. Круговой блокировки нет.
