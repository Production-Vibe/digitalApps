# ADR-004: Манифест деплоя — трассируемость «git-коммит ↔ версия /exec»

**Статус:** Принято (2026-09-07, вариант A — лёгкий манифест деплоя).
**Дата:** 2026-09-07.

## Контекст

Деплой выполняется **вручную** (ADR-001, `docs/specs/adr/deploy-manual.md`):
правка `modules/*.md` → синтакс-проверка → копирование тела в редактор Apps
Script → «Новая версия» активного `/exec`. Класпа и CI нет, связь
«git-версия ↔ что реально выкачено в `/exec`» не фиксируется автоматически.

Текущее положение:
- `docs/reports/STATUS.md` указывает «последний commit/тег» (`5022dc9`, `v0.2-e2e`)
  и активный URL `/exec`, но **это ручная запись**, а не процедура.
- Фактический деплой «по факту копирования» может отставать от git или, наоборот,
  обгонять его (выкатили, забыли закоммитить/подписать). По одному `STATUS.md`
  нельзя достоверно понять, **какая версия кода сейчас в проде**.
- Версии `/exec` в Apps Script нумеруются автоматически (1, 2, …), но **не
  привязаны к git** и не имеют комментариев о содержимом (если их не писать вручную).

**Проблема:** отсутствует трассируемость «какой git-состояние соответствует
активному `/exec`». Это самый дешёвый источник неопределённости: «всё работает,
но непонятно что выкачено».

## Решение (варианты)

### Вариант A (рекомендуемый): лёгкий манифест деплоя в STATUS/файл

- Завести небольшой файл `docs/reports/deploy-manifest.md` (или блок в
  `STATUS.md`) — **журнал, а не только «последний деплой»**: каждая строка —
  один деплой, последняя — текущее состояние.
- Заполняется **в момент фактического завершения деплоя** (сразу после шага
  «Новая версия» в редакторе), не «авансом». Кортеж на деплой:
  - дата/время деплоя;
  - активный URL `/exec` (или его хвост);
  - git-состояние **на момент деплоя**: ближайший `commit/tag` (`v<N>-<этап>`)
    **и пометка о чистоте дерева** (деплой часто идёт ДО коммита — фиксируем
    хэш дерева/статус незакоммиченных правок, чтобы запись была честной);
  - список изменённых модулей;
  - **обязательное** поле «номер новой версии Apps Script» (из редактора) —
    единственный жёсткий артефакт деплоя; без него строка не считается
    зафиксированной.
- Процедура добавляется в `deploy-procedure.md` (шаг: заполнение манифеста).
- **Плюсы:** минимальные затраты (нет clasp/CI), закрывает главную боль —
  «что сейчас в проде», и видна история деплоев. **Минусы:** остаётся ручной
  шаг (но он строго по месту деплоя и вместо «забыть»).

### Вариант B: машиночитаемый манифест `docs/reports/deploy.json`

- Аналогично A, но в JSON (дата, url, commit, tag, modules, appsScriptVersion),
  позволяет будущую автоматизацию/проверку согласованности скриптом
  (`check-deploy.js`).
- **Ограничение проверки (честно):** скрипт может сверить только
  **git ↔ манифест** (что манифест соответствует git-состоянию). Сравнить git с
  реальным содержимым `/exec` вручную невозможно — проверка не «доказывает», что
  выкачено именно это, а только что манифест не врёт.
- **Плюсы:** пригодно для проверок согласованности; **Минусы:** JSON менее
  читаем для человека; всё равно ручное обновление.

### Вариант C: вернуть clasp / полный CI (откладывается)

- Автоматический деплой из всего репо. **Требует** настройки clasp с аккаунтом
  владельца таблицы и новый ADR (как прямо указано в ADR-001 «Следствия для
  будущего»). На текущем этапе — избыточно, не выбран (мейнтейнер один, ручной
  деплой работает).

## Последствия

- Для A/B: в `docs/reports/STATUS.md` поле «Последний деплой» становится
  фактической записью по манифесту, а не «зафиксированный commit вообще».
- Уменьшается риск диагностики «Загрузка…» (см. `МАСТЕР-ДИАГНОСТИКА.md`): манифест
  показывает, совпадает ли `/exec` с ожидаемой версией.
- Никаких изменений в коде-модулях — только документация и процедура.

## Следствия для будущего

- При будущем выборе автоматизации деплоя манифест-файл послужит «данными для
  проверки», а не заменой.
- Теги этапов (`v<N>-<этап>`) и манифест взаимодополняют: тег говорит «этап
  завершён в git», манифест — «этот этап выкачен в прод».

## Связанные пути

- `docs/specs/adr/deploy-manual.md` — почему деплой ручной.
- `docs/reports/STATUS.md` — где фиксировать «актуальный деплой».
- `.opencode/skills/digitalapps-deploy/references/deploy-procedure.md` — куда
