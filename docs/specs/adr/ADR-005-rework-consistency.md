# ADR-005: Консистентность статуса «rework» между моделями нарядов

**Статус:** Черновик (для обсуждения, решение ещё не принято).
**Дата:** 2026-09-07.

## Контекст

Статус **`rework`** («Доработка», возврат ОТК) реализован **только в одной из
двух моделей нарядов**:

- **`Наряды`** (`SHEET_NARYADY`) — статус `rework` существует:
  - `OtkUI.otkReturnToRework` ставит `rework` + причину
    (`modules/OtkUI.md:77-80`);
  - `data-model.md`: статусы `created / in_progress / waiting_otk / rework / closed`;
  - оператор видит «Доработка» (`OperatorUI.md` статус-бейдж `rework`).
- **`WorkOrders`** — статус `rework` **отсутствует**:
  - `data-model.md`: только `created / in_progress / waiting_otk / closed`;
  - возврат на доработку `OtkUI` пишет только в `Наряды`, а `WorkOrders`
    остаётся в прежнем статусе (`waiting_otk` или `in_progress`).

Это прямое следствие двух систем учёта (см. ADR-003). Пока наряды живут в
разных статусных моделях, `rework` в `WorkOrders` не отражается, и картина
«что на доработке» расходится между shift/master (читают `WorkOrders`/Dashboard)
и otk (читает `Наряды`).

## Решение (варианты)

> **Вариант C можно принять сразу** (общий словарь статусов, независим от
> ADR-003). Варианты A/B — после выбора канонической модели в ADR-003.

### Вариант C (рекомендуемый сейчас, независимо от ADR-003): унифицировать через общий словарь статусов

- Выделить единый перечень статусов наряда (например, `created → in_progress →
  waiting_otk → rework → closed` + варианты) и держать его в одном месте
  (`Config`/спека), а листы-«проекции» маппят его на свои значения.
- **Почему независим от ADR-003:** общий словарь полезен при любом выборе
  источника истины; может быть принят и реализован **немедленно**, до решения
  по канону. A/B ниже — как развитие после ADR-003.
- **Плюсы:** избегаем рассинхронизации словарей; основа для валидации и E2E.
  **Минусы:** требует минимального рефакторинга статусных проверок по модулям.

### Вариант A (после выбора канона = `WorkOrders` из ADR-003): добавить `rework` в модель `WorkOrders`

- Добавить статус `rework` в перечень статусов `WorkOrders` и в `data-model.md`.
- Возврат на доработку (ОТК) обновляет **обе** записи (в каноне `WorkOrders` —
  источник, в проекции `Наряды` — зеркало), ставит причину.
- Оператор после доработки снова переводит наряд в `waiting_otk`.
- **Плюсы:** единая статусная модель по всему цифровому потоку; master/shift
  видят доработку; меньше расхождений. **Минусы:** требует правил
  синхронизации `WorkOrders ↔ Наряды` (ADR-003).

### Вариант B (если канон = `Наряды`, ADR-003/Вариант B): оставить `rework` в `Наряды`, маппировать в `WorkOrders`

- `WorkOrders` не знает `rework` как таковой; при возврате ОТК статус в
  `WorkOrders` возвращается в `in_progress` (или вводится отдельное поле
  «доработка»), а в `Наряды` — собственный статус `rework`.
- **Плюсы:** не трогает существующую учётную логику ОТК/VBA.
  **Минусы:** сохраняется расхождение словарей статусов; требует маппинг-слоя.

## Последствия

- Для C (немедленно): ввести общий словарь статусов (в `Config`/спеке);
  `data-model.md` фиксирует единый перечень.
- Для A (после ADR-003): правки в **`NaryadAPI.setNaryadStatus`** (валидация
  `rework`), **`OtkUI`** (возврат `rework` обновляет и `WorkOrders`),
  **`OperatorUI`** (бейдж «Доработка»), фильтры **`OtkUI`** (таб «Доработка»),
  и — видимость в **`MasterUI`/`Planning`** (Dashboard/shift видят, что наряд
  на доработке, а не «в работе»). Затрагиваются те же точки, что и в ADR-003.
- Для B (если канон = `Наряды`): слой маппинга статусов, тест согласованности.
- **Отображение rework в Dashboard/Planning (открытый вопрос к обсуждению):**
  что должен показывать Dashboard на наряде-«Доработка» (отдельная категория?
  как подстатус «В работе»?) — зафиксировать при реализации A/C.
- Во всех случаях: сквозной E2E-сценарий «приём → брак → доработка → закрытие»
  должен проверять, что статус доработки виден в обеих моделях (и на смене).

## Следствия для будущего

- Решает «тлеющий» техдолг расхождения моделей; тесно связано с ADR-003.
- Обновить `docs/specs/data-model.md` (таблица статусов) при принятии.
- Порядок принятия: **C — независимо и сразу; A/B — после выбора канона
  в ADR-003**. Зависимость от ADR-003 односторонняя, круговой блокировки нет.
