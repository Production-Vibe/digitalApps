# ADR-008: Роль Admin (superuser) и самостоятельная регистрация операторов

Статус: принято (21.09.2026).

## Контекст

До этапа 14 все роли (`master`/`shift`/`operator`/`otk`) заводились только из
сида — для реального процесса этого недостаточно: операторы приходят сменными,
списки теряют актуальность, а роли назначает один ответственный. Требуется:

- **операторы** могли заводить себе аккаунты сами (простая самозапись, без прав
  на роли);
- единый **администратор аккаунтов** (создание ролей, смена роли, сброс пароля,
  деактивация);
- контроль отключения доступа (увольнение/перевод) без удаления записей.

Рассматривалось: (а) открытая регистрация любой роли — отклонено: роль
master/shift/otk должен назначать ответственный; (б) отдельная серверная роль
«HR» без доступа к производству — излишне для нынешнего масштаба; (в) каскад
ролей без суперпользователя — усложняет администрирование.

## Решение

1. **`admin` — суперпользователь** (`EmployeeRole` += `admin`, только сидом/скриптом):
   - проходит **любой** ролевой фильтр `requireAuth(...roles)` и любую
     роль-страницу;
   - домашняя страница — `/admin` (UI аккаунтов сотрудников);
   - **завести второго `admin` через UI нельзя** — ни регистрация, ни форма
     админ-панели не предлагают роль `admin`.
2. **Оператор — самозапись** через `POST /api/register` (таб «Регистрация» на
   `/login`): роль всегда `operator` (сервер игнорирует роль в теле), валидация,
   дубль логина → 409, авто-вход.
3. **master/shift/otk** создаются администратором (`/api/admin/employees`:
   create / смена роли / сброс пароля).
4. **Деактивация** — `Employees.isActive Boolean @default(true)`: `false` →
   вход/сессия 403, скрытие из списков; сам-деактивация администратора запрещена.

## Последствия

- `requireAuth(...roles)` и клиентские guards ролевых страниц принимают `admin`;
  для логики каждой роли `admin` — «гость» (может смотреть, вводить ролевые
  действия не обязан).
- `isActive=true` — базовый фильтр везде, где список сотрудников показывается
  участникам потока (`GET /api/employees`).
- Сид содержит аккаунт `admin` с демо-паролем `121212` (пароль всех сотрудников
  разом — `npm run passwords -- <пароль>`, минимум 6 символов; скрипт обходит
  **все** строки `Employees`, включая зарегистрированных через UI операторов).
  Перед публикацией демо-пароль сменить на реальный.
- Seed задаёт пароль **только при создании** аккаунта (`upsert` с `update: {}`),
  поэтому деплой/рестарт контейнера не сбрасывает изменённые пароли.
