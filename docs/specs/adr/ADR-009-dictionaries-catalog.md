# ADR-009: Справочники каталога + автогенерация кода

Статус: принято (25.09.2026).

## Контекст

После CRUD каталога (Этап 16) запись номенклатуры в `Catalog` полностью
свободна: 5 «словарных» полей (`blankType/material/materialGrade/blankSize/
priority`) вводились произвольным текстом, а код подписывается вручную.
Следствия: мусор в данных (`#N/A`, `0`, `—`, числа), рассинхрон написания
(`КРУГ`/`Круг`), риск битых ссылок при редактировании кода.

Рассматривалось: (а) FK-связь `Catalog → DictionaryValue` — отклонено:
существующие строки — String, введение FK потребовало бы миграции значений и
жёсткой референции, несовместимой с Excel-импортом (Excel = резерв);
(б) ручной ввод кода оставить всем — противоречит стабильной идентичности;
(в) «папки»-группы дерева — отклонено: узел реальной записи остаётся
полноценной позицией.

## Решение

1. **Словари — без FK.** Модель `DictionaryValue` (13-я; `type/value/synonyms/
   isActive/sort`, `@@unique([type, value])`); строки `Catalog` остаются `String`.
2. **Код — автогенерация от дерева** (`lib/codes.ts`, чистые функции):
   `max(прямые дети)+1`, разделитель `/`, top `max(1..22)+1 → 23`; удалённые
   номера не переиспользуются.
   Ввод кода руками — **только admin** (импорт/миграция/легаси); master обязан
   слать код из `POST /api/catalog/next-code` (сервер пересчитывает сам, иной
   `code` → 400 «Код позиции формируется автоматически»). Корневое создание
   master — тоже по `next-code` (top-уровень).
3. **Материализация контейнеров.** Узел дерева существует как префикс кода без
   строки в `Catalog`; при создании под ним сервер `upsert`-ит отсутствующие
   строки-контейнеры по пути (код + имя, техданные пустые), то же в
   `missingPathRows` на `PUT`-каскаде; в POST-ответ включается
   `materialized: string[]`, в `next-code` — `wouldMaterialize: string[]` (превью).
4. **«Не задано» = пустая строка** `''`; отдельных значений-заглушек в словарях
   нет; валидны пустые значения всегда.
5. **Валидация словарей строгая в UI/API**, лояльная в импорте:
   - UI/`POST/PUT /api/catalog` (`toCanonical`): непустое значение обязано
     совпасть с активным значением словаря (по значению или синониму), иначе
     400 `{error, field}`; на запись сохраняется канон.
   - `resolveOrCreate` (VBA/Excel-импорт): неизвестное значение автоматически
     создаётся активным в словаре (`dictAdded`) — Excel остаётся источником
     новых марок/типов, интеграция не рвётся.
6. **Роли**: `GET /api/dictionaries/:type` и quick-add (`POST`) — `master`
   (+admin); `PUT`/`deactivate` — `admin`; деактивированные значения не
   предлагаются и не принимаются, существующие строки каталога не трогаются.
7. **Чистка данных** — идемпотентный `npm run dict:migrate`
   (`normalize-catalog-dicts.ts`, `--dry` для предпросмотра): мусор
   (`#N/A/0/—/числа`) → `''`, синонимы-варианты → канон; `Catalog.code` не
   изменяется ни при каких условиях (ссылки `Launches/WorkOrders/PrintQueue/
   Queue` целы).

## Последствия

- `Catalog.code` остаётся стабильной идентичностью; ручная смена кода — только
  с привилегией admin (каскад `moved` сохранился).
- `test_catalog_crud.py` (Этап 16) переведён на создание/смену кода через admin
  — ручной код больше не разрешён master.
- PostgreSQL String[] (`synonyms`) — ок для PostgreSQL; другие БД потребовали
  бы отношения.
- Введена 13-я модель; `DICT_TYPES`/`DICT_LABELS` — единый словарь типов в
  `server/src/lib/dict.ts`.
