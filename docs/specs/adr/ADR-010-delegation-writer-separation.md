# ADR-010: Разделение писателей в контуре делегирования

Статус: принято (13.10.2026).

## Контекст

Двухконтурное делегирование уже существует: T1 (`nda-planner`) ведёт диалог и
планирует, T2 (`nda-executor`) исполняет задачи из файловой очереди
`.opencode/queue.jsonl` (pull-модель, `docs/specs/agent-delegation.md`). Причина
контура — деградация одного длинного диалога после повторных компакшенов:
накопление шума и галлюцинаций. Но у исходной схемы остались четыре слабых места:

1. T1 — по-прежнему один длинный диалог: построенная архитектура живёт только в
   чате и теряется при ре-сиде/падении сессии (шум переехал из T2 в T1).
2. Бриф — проза без проверяемых требований: исполнитель может «достроить» его и
   уйти в галлюцинации.
3. Нет сигнала, **какой контур** дал сбой (плохой бриф vs неудачное исполнение).
4. Промоушен решения в `docs/specs/`/ADR не имел владельца: T1 по permission не
   может править проект, а отдельного пути записи не было.

## Решение

1. **Инвариант «T1 не правит проект».** `edit` планировщика ограничен
   `.opencode/**` (design-док + очередь). Любая запись в проект (`docs/**`,
   `server/**`) выполняется только T2. Писатели разведены: T1 — дизайн и очередь,
   T2 — проект и `result.md`; каждый артефакт имеет одного владельца.
2. **Живой design-документ — сид T1.** `.opencode/design/<slug>.md` (gitignored,
   один файл на активную инициативу) содержит три слоя: (1) застывшее —
   промоутится в `docs/specs/`/ADR и вычищается; (2) в работе; (3) открытые
   вопросы. Документ ведётся непрерывно, поэтому ре-сид T1 не зависит от
   точного момента чекпоинта; чекпоинт идёт по детерминированному прокси (число
   застывших решений/выданных задач), а не по самомодельной оценке токенов.
3. **Промоушен — через T2.** T1 формулирует текст решения в design-доке,
   пользователь подтверждает, запись в `docs/specs/`/ADR исполняет делегированная
   задача T2. Permission планировщика не смягчается; второй писатель в `docs/` не
   появляется.
4. **Бриф — контракт приёмки.** Чеклист: одна связная цель; ≥1 acceptance-команда;
   ≤1 модуль/зоны проекта; обязательна оценка размера; проверяемый критерий
   успеха. T2 проверяет чеклист **до** исполнения; при провале — статус `rejected`
   (без импровизации), перечень нарушенных пунктов идёт в `result.md`/`error`.
5. **Статусная модель очереди.**
   `pending → claimed → in_progress → done | failed | rejected`.
   `failed` = бриф валиден, исполнение не удалось (чинить T2); `rejected` = бриф
   невалиден (чинить T1). Повтор после `rejected` — тот же `taskId`: `context.md`
   правится, строка возвращается в `pending`, история попыток копится.
6. **`/handoff` — транспорт наружу.** Команда `/handoff` служит разовому переносу
   работы в другой харнесс/каталог и в контуре T1→T2 не используется: адресаты
   разные (design-док читает сам T1, `/handoff` — внешний получатель).

## Последствия

- У каждого артефакта ровно один писатель: дизайн/очередь — T1, проект — T2;
  конфликт двух писателей в `docs/` исключён.
- Промоушен перестал быть побочной операцией: это обычная задача очереди с
  брифами «записать решение X в `docs/specs/…`, вот текст, вот acceptance».
- Runtime-состояние контура (`.opencode/design/`, `tasks/`, `logs/`) — gitignored;
  `queue.jsonl` остаётся трекаемым как витрина контракта.
- Проверка — живой двухоконный смоук (агенты суть промпты, а не код):
  создание design-дока, `rejected` заведомо плохого брифа → правка того же
  `taskId` → `done`, промоушен-задача.
