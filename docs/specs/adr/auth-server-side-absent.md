# ADR-002: Серверная авторизация в текущем виде отсутствует (роль из URL)

**Статус:** Принято (зафиксировано ограничение).
**Дата:** 2026-09-04.

**Контекст:** В «ЦифровойНаряд» авторизация выполняется на клиенте: роль
передаётся через URL-параметр (`?page=...&role=otk`, `&name=...` — см.
`docs/specs/roles.md` и `modules/Auth.md` `doGet`). Серверная сессия/токен
отсутствуют: вызовы `google.script.run` и `doPost` не аутентифицируют субъекта
на бэкенде. В Блоке 5 этапа «Багфиксы 1–5» для закрытия дыры «любой POST
`close_naryad`» в `modules/NaryadAPI.md` добавлен хелпер `isRole(user,
expectedRole)`, который сверяет поле `closed_by` с листом `Сотрудники`.

## Решение

Ограничение зафиксировано, а не закрыто полностью. `isRole()` — **частичное
усиление**: оно требует, чтобы в `closeNaryad` был передан `closed_by`,
соответствующий otk-пользователю из `Сотрудники`. Это защищает от «голого»
вызова без субъекта, но **не защищает от подделки поля** (произвольный
`closed_by`-otk или спуфинг роли в URL), т.к. настоящая серверная сессия не
строится.

Полноценная серверная авторизация (токен/сессия, проверка на бэкенде каждого
вызова) — **отдельная архитектурная задача**, вне рамок текущего цикла.

## Последствия

- Безопасность основана на договорённости об аккаунт-инфраструктуре Google
  (доступ к самому `/exec` ограничивается настройкой развёртывания) плюс
  базовая проверка роли через `isRole` для чувствительных операций (`closeNaryad`).
- Роль в UI остаётся спуфируемой (любой запрос с `?role=master`). Для закрытой
  служебной инфраструктуры приемлемо, для публичного доступа — нет.
- `isRole()` — переиспользуемый хелпер; использовать его и в будущих операциях,
  требующих ролевой проверки.

## Следствия для будущего

- При разработке ОТК-интерфейса и при любом внешнем (публичном) доступе —
  реализовать серверную авторизацию: отдельный ADR + фактическая проверка
  субъекта на бэкенде (например, сквозной токен сессии), а не только роли в URL.
- Добавлять `isRole()`-проверки в чувствительные бэкенд-функции по мере их
  появления.

## Связанные пути

- `modules/Auth.md` — `doGet`: роль/имя из URL-параметров; `checkAuth()` по `Сотрудники`.
- `modules/NaryadAPI.md` — `isRole()`, `closeNaryad()`.
- `docs/specs/roles.md` — роутинг ролей по `?page=`.
- `modules/Config.md` — `SHEET_EMPLOYEES`.
