# Делегирование «планировщик → файловая очередь → исполнитель» (два терминала, pull)

Статус: спецификация инструментальной наработки (не этап приложения —
бизнес-флоу и `server/**` не менялись). Источник правды — фактические файлы
`.opencode/agents/nda-planner.md`, `.opencode/agents/nda-executor.md`,
`.opencode/queue.jsonl`.

## Зачем и какая модель

Модель: **пользователь → планировщик (T1) → запись в файловую очередь →
исполнитель (T2, сам подхватывает)**.

- Пользователь общается только с планировщиком: разбор задачи, уточнения,
  план на согласование.
- Планировщик **не пишет код проекта и не правит файлы проекта** (`edit` в
  проекте — deny; разрешена запись только в `.opencode/**` для брифингов и
  очереди, `bash` — ask) — он только планирует и делегирует записью в
  файловую очередь.
- Исполнитель — **долгоживущий интерактивный агент во втором окне**:
  самостоятельно (polling каждые ~3–5 сек) подхватывает первую
  `pending`-задачу, выполняет её (правка файлов, проверки) и пишет результат
  в очередь и `result.md`.

Зачем так:

- **Никакого копипаста.** Контекст передаётся структурированным брифингом
  (`context.md` + одна JSON-строка в `queue.jsonl`), а не вставками между
  окнами.
- **Разделение ролей** «диалог/план» и «код/проверки»: у планировщика правка
  проекта запрещена permission'ом — правки не идут «с двух сторон».
- **Раздельные процессы.** T1 и T2 — два независимых интерактивных окна
  opencode; нет вложенных процессов, MCP-моста, мьютекса и таймаутов
  синхронного вызова.
- **Очередь — источник правды.** FIFO-порядок, статусы и история событий
  лежат на диске и видны любым читателем (`type .opencode\queue.jsonl`).

## Схема потока

```
Пользователь
   │  диалог: задача → план → согласование
   ▼
T1: opencode --agent nda-planner    (терминал 1, интерактивный)
   │  1) write .opencode/tasks/<TASK_ID>/context.md   (брифинг)
   │  2) append 1 JSON-строку в .opencode/queue.jsonl  (status:"pending")
   ▼
Файловая очередь .opencode/queue.jsonl   (append-only, FIFO)
   ▲
   │  опрос каждые ~3–5 сек, берёт первую status=="pending"
T2: opencode --agent nda-executor   (терминал 2, интерактивный, цикл)
   │  claim → in_progress → выполнение (edit/bash по брифингу)
   │  write .opencode/tasks/<TASK_ID>/result.md
   │  обновить строку: status → "done"|"failed"; append событий в
   │  .opencode/logs/activity.jsonl
   ▼
T1: по запросу пользователя читает очередь/result.md → сводка
```

## Как запускать два терминала

**T1 — планировщик (интерактивный диалог):**

```powershell
cd C:\Projects\digitalApps
opencode --agent nda-planner
```

**T2 — исполнитель (автономный цикл):**

```powershell
cd C:\Projects\digitalApps
opencode --agent nda-executor
```

Оба окна — интерактивные и долгоживущие. T2 держать открытым, пока идёт
работа: он сам ждёт pending-задачи (блокирующий опрос), выполняет и сразу
возвращается к ожиданию. Закрытие T1 (планировщика) очередь не ломает:
задачи уже в файле, исполнитель доработает их при следующем запуске.

## Контракт очереди `.opencode/queue.jsonl`

Формат — JSON Lines (одна JSON-строка на задачу, UTF-8, append-only).

| Поле | Тип | Смысл |
|---|---|---|
| `taskId` | string | `TASK-YYYYMMDD-HHmmss` (коллизия секунды → суффикс `-N`) |
| `status` | string | `pending → claimed → in_progress → done \| failed` |
| `claimedBy` | string\|null | кто захватил (у нас всегда `nda-executor`) |
| `claimedAt` / `startedAt` / `completedAt` | string\|null | ISO8601-моменты переходов |
| `contextPath` | string | путь к брифингу `.opencode/tasks/<TASK_ID>/context.md` |
| `resultPath` | string\|null | путь к итогу `.opencode/tasks/<TASK_ID>/result.md` |
| `goal` | string | одна строка — суть задачи (для человека, смотрящего в очередь) |
| `artifacts` | array | созданные/изменённые файлы |
| `error` | string\|null | текст ошибки при `failed` |
| `createdAt` | string | ISO8601 момент постановки |

Правила гонки и порядка:

- Берётся **первая** строка со `status=="pending"` (строго FIFO).
- Claim/finish — **замена одной строки целиком** с сохранением позиции;
  чужие строки не трогать, не переставлять, не удалять. Новые задачи —
  только append в конец.
- Если у `pending` уже заполнен `claimedBy` (гонка двух исполнителей) —
  строку пропустить и взять следующую. **Открытый риск:** два одновременных
  окна T2 не сериализованы централизованно (MCP-моста с мьютексом больше
  нет) — штатно держать ровно одно окно исполнителя.

## Брифинг `context.md` (Link, don't embed)

Секции: `Goal`, `Requirements`, `Acceptance Criteria`, `Inputs/Context`,
`Constraints`, `Artifacts Expected`, `Return`. Существующие файлы —
Markdown-ссылками, без вставки больших кусков кода.

Итог исполнения — `result.md`: `Status` (done/failed), `Summary`,
`Artifacts`, `Notes` с фактическим выводом проверок.

## Таблица permission и зачем каждый запрет

| Инструмент | nda-planner (primary) | nda-executor (primary) | Зачем именно так |
|---|---|---|---|
| `edit` | allow **только** `.opencode/*` (`.opencode/**/*`), всё остальное — deny | allow | Планировщик пишет только брифинг/очередь, файлы проекта — только исполнитель; исключены два «владельца» правок |
| `read`/`glob`/`grep`/`list` | allow | allow | Планировщику — чтение кода для составления брифинга; исполнителю — полный доступ на чтение |
| `bash` | **ask** (см. ниже) | allow (`git push*`, `rm -rf *` → ask) | Команды планировщика не должны выполняться без участия пользователя; у исполнителя `bash` — инструмент проверок (`npm run build` и т.п.) |
| `task` | deny | deny | Слой агентов ровно два, под-агенты ломают схему |
| `question` | allow | deny | Исполнитель не общается с пользователем: при неоднозначности — отчёт «ОГРАНИЧЕНИЕ» |
| `dispatch_tasks`, `register_task_group`, `execute_next_group`, `discard_remaining_groups`, `orchestrator_execute_task`, `submit_task_result` | **deny** | **deny** | Оркестрационные тулзы прежней (MCP/push-) модели **запрещены явно у обоих**: без deny при `* allow` модель могла вызвать `dispatch_tasks` (ошибка `task.dependsOn`) вместо записи в очередь |

### Почему `bash: ask`, а не `deny` у планировщика

Free-tier gateway (`opencode.ai/zen/v1/chat/completions`) детерминированно
отвечает **403 «OpenCode's free tier can only be used from within OpenCode»**
на любой запрос, из которого отсутствует тул `bash`. Обход — держать тул
`bash` присутствующим и ограничивать его `ask`. Семантика: в интерактивном
T1 каждый вызов `bash` требует подтверждения; промпт запрещает планировщику
команды, фактический запрет сохранён.

### Почему агенты названы `nda-*` (конфликт с плагином argos)

Проектные `.opencode/agents/nda-planner.md` и `nda-executor.md`
названы с префиксом `nda-`, чтобы не затеняться одноимёнными агентами
плагина `@nest4869/argos` (`architect (subagent)`, `orchestrator (primary)`).
Роли названы по фактической функции (`planner`/`executor`), а не по
`architect`/`orchestrator`: первый агент планирует и делегирует, второй —
исполняет одну задачу (не оркеструет воркеров). Оба проектных агента —
`mode: primary` (иначе `--agent` откатывается на default: «is a subagent…
Falling back»). Проверяется обычным `opencode agent list`.

## Архив: MCP-мост (push-модель)

Прежняя реализация (синхронный вызов `orchestrator_execute_task` через
stdio-мост `tools/mcp-orchestrator/`) **сохранена в ветке
`archive/mcp-orchestrator`** и из `main` удалена: папка моста, блок
`mcp.orchestrator` в `opencode.json`, лаунчеры `nda-planner.cmd` /
`nda-run.ps1` / `run-delegation.cmd`, `.vscode/tasks.json`, `манифест.md`.
Исторические протоколы верификации моста — там же
(`tools/mcp-orchestrator/verification/`).

Что переехало в модель (и сохранилось):

- **Анти-рекурсия** — теперь на уровне permission: оба агента имеют
  `orchestrator_execute_task: deny` и запрет всех оркестрационных тулзов.
- **Одна задача за раз** — фактически обеспечивается правилом «держать одно
  окно T2 + FIFO-захват первой pending» (см. риск гонки выше).
- **Синхронное ожидание и таймауты (`-32001`, `ORCH_NESTED`,
  `mcp.orchestrator.timeout`)** — отпали как класс: задачи не блокируют
  планировщика, ожидание — файловое.
- **Режим submit/poll** — стал основной моделью (это и есть очередь).

## Известные ограничения и риски

1. **Нет централизованного мьютекса.** Два одновременных окна T2 могут
   захватить одну задачу (защита только «если `claimedBy` уже заполнен —
   пропустить», а не атомарный compare-and-swap на диске). Держать одно окно
   исполнителя.
2. **Нет подтверждения доставки.** Планировщик не ждёт результата: статус
   пользователь спрашивает отдельно (T1 читает очередь/`result.md`).
3. **Перезапуск T2 теряет поллинг-цикл**: после запуска агент начнёт цикл
   с п.1 инструкции — очередь доводит до конца; задачи, брошенные в
   `in_progress` при убийстве окна, останутся в `in_progress` навсегда
   (ручной сброс строки в `pending` — штатная операция).
4. **Стоимость polling-холостых циклов**: блокирующий bash-опрос тулзом —
   дёшево (одна команда до появления pending), но при многодневно открытом
   T2 агент «просыпается» на каждую задачу заново — это нормально.

## Проверка (актуальная)

Живой смоук модели делегирования:

1. T2 запущен и ждёт (`queue.jsonl` пуст) — команда ожидания блокируется.
2. В T1: план → согласие → задача → в `queue.jsonl` строка `pending`,
   `context.md` создан; планировщик **не** вызывает оркестрационные тулзы.
3. T2 подхватывает: `claimed → in_progress → done`, `result.md` с выводом
   проверок, события в `activity.jsonl`.
4. T1 читает результат и выдаёт сводку.
5. `opencode agent list` — оба агента `nda-*` primary с deny
   оркестрационных тулзов.

## Handoff (файловый) и превентивное предотвращение компакшена

- **Файловый handoff.** Передача состояния между T1 (nda-planner) и T2 (nda-executor) реализована через файловую границу: `context.md` (брифинг) + JSONL-очередь (`.opencode/queue.jsonl`) + `result.md`. Это явный handoff без потерь на многоуровневый compaction.
- **Превентивный порог 55–60%.** В долгоживущей интерактивной сессии T2 при приближении к ~55–60% контекста модели рекомендуется довести текущую задачу до логической границы (`done`) и взять следующую `pending` с чистым контекстом. При headless-прогоне `opencode run --agent nda-executor` на 1 задачу это правило менее критично.
- **Расщепление.** Крупные задачи стоит дробить на более мелкие (грануляция) с учётом контекста. Если исполнитель видит избыточную гранулярность брифинга, он указывает рекомендацию по расщеплению в `result.md` (инициатор расщепления — `nda-planner`).
