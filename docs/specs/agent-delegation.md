# Делегирование «архитектор → MCP-мост → оркестратор» (два терминала)

Статус: спецификация инструментальной наработки (не этап приложения —
бизнес-флоу и `server/**` не менялись). Источник правды — фактические файлы
`tools/mcp-orchestrator/index.mjs`, `.opencode/agents/nda-architect.md`,
`.opencode/agents/nda-orchestrator.md`, `opencode.json → mcp.orchestrator`.

## Зачем и какая модель

Модель: **пользователь → архитектор (T1) → делегация через MCP → оркестратор
(исполнитель)**.

- Пользователь общается только с архитектором: разбор задачи, уточнения,
  план на согласование.
- Архитектор **не пишет код и не трогает файлы** (`edit`/`task` = deny, `bash`
  = ask — см. «Почему не deny» ниже) — он только планирует и делегирует
  вызовом `orchestrator_execute_task`.
- Оркестратор — headless-исполнитель: получает одну чёткую задачу, читает/правит
  файлы, запускает проверки и возвращает краткое резюме с фактическим выводом.

Зачем так, а не «один агент на всё»:

- **Никакого копипаста.** Контекст передаётся структурированным вызовом тула
  (`task`, при необходимости `context`), а не вставками между окнами или
  агентами; пользователь получает компактную сводку архитектора, а не сырой
  поток `tool_use` вложенного процесса.
- **Единая точка исполнения.** Вся реализация идёт через один мост: мьютекс
  (одна задача за раз), tee-лог, git-дельта изменений — собраны в мосте, а не
  размазаны по сессиям.
- **Разделение ролей** «диалог/план» и «код/проверки»: у архитектора нет
  инструментов редактирования, поэтому правки не идут «с двух сторон» —
  ручной копипаст работы между архитектором и оркестратором исключён.

## Схема потока

```
Пользователь
   │  диалог: задача → план → согласование
   ▼
T1: opencode --agent nda-architect    (терминал 1, интерактивный)
   │  вызов тула: orchestrator_execute_task(task, context?, timeoutMs?)
   ▼
opencode (хост T1) поднимает stdio-мост:
node tools/mcp-orchestrator/index.mjs   (opencode.json → mcp.orchestrator)
   │  JSON-RPC over stdio: tools/call execute_task
   │  мьютекс: одна задача за раз (параллельный вызов → «занят»)
   │  spawn: opencode run --format json --agent nda-orchestrator "<промпт>"
   │  cwd = корень проекта (каталог, где найден opencode.json)
   │  env: ORCH_NESTED=<глубина+1> — анти-рекурсивный guard (см. ниже)
   ├─────────── tee живого вывода ───────────► logs/orchestrator.log
   │                                                ▲
   │                                                │ T2: npm run watch
   │                                                │ (только чтение файла)
   ▼
Оркестратор (headless): read/edit/bash … выполняет задачу
   │  дочерний процесс завершён
   ▼
Структурированный ответ архитектору (JSON-результат MCP):
success, summary, files_changed, exitCode, durationMs, stdout, error
   │
   ▼
T1: архитектор выдаёт пользователю краткую сводку
    (что сделано, файлы, результаты проверок)
```

## Как запускать два терминала

**T1 — архитектор (интерактивный диалог):**

```powershell
cd C:\Projects\digitalApps
opencode --agent nda-architect
```

(или `nda-architect.cmd` — обёртка-лаунчер; либо просто `opencode` + Tab до
`nda-architect`).

**T2 — наблюдение за оркестратором (живой лог):**

```powershell
cd C:\Projects\digitalApps\tools\mcp-orchestrator
npm run watch
```

`npm run watch` — это обёртка над
`Get-Content -Wait -Tail 120 logs/orchestrator.log`: последние 120 строк лога
с обновлением в реальном времени, остановка — Ctrl+C.

### Честное ограничение: T2 — окно наблюдения, а не чат

opencode **не умеет подключаться к уже запущенному stdio MCP-серверу**: stdio —
это двунаправленный канал один-на-один между хостом и сервером, второй клиент
к нему прицепиться не может. Поэтому отдельного «интерактивного разговора с
оркестратором» через T2 не существует. T2 — окно **наблюдения**: вы видите живой
ход работы вложенного `opencode run` (spawn, git, `data|`, `tool|`, итог задачи).

При закрытии T2 делегация **не ломается**: мост поднимает сам opencode в T1,
лог пишется на диск независимо от читателя, `npm run watch` лишь читает файл.

## Контракт тула `orchestrator_execute_task`

Имя в сессии архитектора — `orchestrator_execute_task` (MCP-сервер
`orchestrator` + тул `execute_task`).

**Вход:**

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `task` | string | да | Текст задачи для вложенного `opencode run`; без него вызов отклоняется (`MCP error -32602 … Required at task`) |
| `context` | string | нет | Дополнительный контекст; добавляется к промпту блоком «Контекст задачи:» |
| `timeoutMs` | number | нет | Таймаут в мс; иначе env `ORCH_TIMEOUT_MS`, иначе `900000` |

**Выход** (JSON в `content[0].text`, `isError` при отказе):

| Поле | Смысл |
|---|---|
| `success` | `true` только если дочерний `opencode run` завершился без ошибки/таймаута |
| `summary` | последний текстовый ответ ассистента вложенного процесса |
| `files_changed` | дельта `git status --porcelain` до/после задачи |
| `exitCode` | код выхода дочернего процесса (`null` при сбое запуска) |
| `durationMs` | длительность задачи |
| `stdout` | живой вывод вложенного процесса, усечён до последних 20000 символов |
| `error` | текст ошибки: сбой запуска / таймаут / ненулевой код / «Внутренняя ошибка моста»; при отказе мьютекса — «Оркестратор занят: другая задача уже выполняется…» |

**Env и таймауты:**

- `ORCH_AGENT` — агент вложенного запуска; дефолт `nda-orchestrator`, пустая
  строка → в `spawn` не добавляется `--agent` (работает встроенный агент).
- `ORCH_TIMEOUT_MS` — дефолтный таймаут, `900000` мс; максимум
  `2147483647`. По превышении мост убивает дерево процессов дочернего `opencode`
  (`taskkill /T /F` на Windows) и возвращает `success=false` с текстом
  «Таймаут … превышен — дочерний процесс opencode убит».
- **`ORCH_NESTED` — анти-рекурсивный guard.** Мост выставляет эту переменную
  (значение = глубина вложенности, стартовая вложенность `2`) в env каждого
  дочернего `opencode run`. Мост, поднятый в окружении с заданным
  `ORCH_NESTED`, **отклоняет** любой вызов `execute_task` на входе с
  `success=false`, `error` «Рекурсия запрещена…» (`isError=true`) — не полагаясь
  на permission `deny` в агентском `.md`. Верхнеуровневый вызов (T1, где
  `ORCH_NESTED` пуст) работает нормально.
- В `opencode.json` у `mcp.orchestrator` задан `timeout: 900000` — таймаут
  MCP-сервера на уровне хоста (ранее `15000` отсекал успешные длинные вызовы
  ошибкой `-32001` ещё до ответа моста).

**Мьютекс:** одновременно выполняется только одна задача. Параллельный вызов
во время занятости возвращает `isError=true` с ошибкой «Оркестратор занят…»,
мост остаётся жив, первая задача дорабатывает.

**Лог:** весь ход задачи tee-ится в `tools/mcp-orchestrator/logs/orchestrator.log`
(каталог `logs/` и `node_modules/` в `.gitignore` моста, в git не попадают).
Строки: `spawn`, `git status`, `data|` (JSON-события), `tool| <имя>`,
`assistant|`, итог `=== Задача #N: конец … ===`.

**Рабочий каталог и корень:** мост поднимается opencode-хостом, корень проекта
определяется подъёмом вверх до `opencode.json` (fallback — `cwd`); дочерний
`opencode run` всегда стартует из корня проекта.

**Подключение в `opencode.json`:**

```json
"mcp": {
  "orchestrator": {
    "type": "local",
    "command": ["node", "tools/mcp-orchestrator/index.mjs"],
    "cwd": ".",
    "enabled": true,
    "timeout": 900000
  }
}
```

## Таблица permission и зачем каждый запрет

| Инструмент | nda-architect (primary) | nda-orchestrator (primary) | Зачем именно так |
|---|---|---|---|
| `edit` | deny | allow | Архитектор не пишет файлы — реализация идёт только через оркестратора; исключает ручной копипаст правок и двух «владельцев» файлов |
| `bash` | **ask** (см. «Почему не deny» ниже) | allow (`git push*`, `rm -rf *` → ask) | Команды у архитектора не должны выполняться без участия пользователя; у оркестратора `bash` — инструмент проверок (`npm run build` и т.п.) |
| `task` | deny | deny | Никому не плодить под-агентов: слой агентов ровно два, вложенность через `task` сломала бы схему и добавила бы второй «владелец» диалога |
| `orchestrator_execute_task` | allow | **deny** | **Анти-рекурсия (слой 1):** permission `deny` убирает MCP-тул из тулсета оркестратора. **Слой 2 — env-guard `ORCH_NESTED` в мосту** (см. «Env и таймауты»): работает даже если deny не применился |
| `question` | (по умолчанию — может) | deny | Оркестратор не общается с пользователем: вместо вопроса возвращает отчёт с пометкой «ОГРАНИЧЕНИЕ» (правило 7 `nda-orchestrator.md`) |
| `read` / `glob` / `grep` / `list` | (по умолчанию) | allow | Оркестратору нужен полный доступ на чтение для выполнения задачи |

Дополнительно `bash` у обоих агентов: `git push*` и `rm -rf *` → `ask`. В
headless-режиме оркестратора никто не может ответить на `ask`, поэтому фактически
это запрет опасных команд; `git commit`/`git push` запрещены и текстом правил
`nda-orchestrator.md`.

### Почему `bash: ask`, а не `deny` у архитектора

Free-tier gateway (`opencode.ai/zen/v1/chat/completions`) детерминированно
отвечает **403 «OpenCode's free tier can only be used from within OpenCode»**
на любой запрос, из которого отсутствует тул `bash`. Это подтверждено A/B-матрицей
пробников: `bash: deny`, `bash: {"*": deny}`, `tools: {bash: false}` → **403**;
`bash: ask`, `bash: allow`, deny `edit`/`task`/`glob` (тулы отсутствуют — не 403)
→ **ok**. Механизм на стороне gateway (сравнение тулсета?), поэтому обход —
держать тул `bash` присутствующим и ограничивать его `ask`.

Семантика для архитектора: в интерактивном T1 каждый вызов `bash` требует
подтверждения пользователя (архитектор его не получает — промпт запрещает
команды); в headless-прогонах `ask` отклоняется автоматически. Фактический
запрет сохранён, детерминированность ранов — тоже.

### Почему агенты названы `nda-*` (конфликт с плагином argos)

Проектные `.opencode/agents/nda-architect.md` и `nda-orchestrator.md` названы
с префиксом `nda-`, чтобы **не затеняться одноимёнными агентами глобального
плагина `@nest4869/argos`** (и др. из `~/.config/opencode/opencode.jsonc`):
плагин регистрирует собственных агентов `architect (subagent)` и
`orchestrator (primary)` с другими режимами и permission — совпадение имён
приводило к тому, что запуск вида `opencode run` + `--agent` с именем
`architect`/`orchestrator` брал плагинный агент (fallback на default, чужие
правила). Подтверждено протоколом
`tools/mcp-orchestrator/verification/2026-10-06-rename-timeout.md` (CQ1):
обычный `opencode agent list` (21 блок) содержит и наши `nda-architect`,
`nda-orchestrator`, и плагинные `architect (subagent)`, `orchestrator
(primary)` — плагин не тронут, конфликт снят только именованием. Оба агента —
`mode: primary` (иначе `opencode run --agent <имя>` откатывается на
default-агента: «is a subagent… Falling back»).

## Жёсткие внешние таймауты — обязательное правило

**Причина:** зависание задачи группы g2 (инструментальная наработка) вызвано
отсутствием жёстких внешних таймаутов у вложенных процессов — ожидание
дочернего процесса шло без ограничения по времени и висело бесконечно.
**Исправлено:** все длинные вызовы обёрнуты жёстким внешним лимитом:

- PowerShell-команды — `Start-Process -PassThru → WaitForExit(ms) → Kill`
  (в протоколе V7 — `ProcessStartInfo → WaitForExit(ms) → taskkill /T /F`);
- оболочка bash — `timeout <с> <команда>`;
- бессрочных ожиданий (`WaitForExit()` без аргумента, `child.on('exit')` без
  таймера) в прогонах и скриптах не оставлять.

Применённые в протоколах внешние лимиты (источник —
`tools/mcp-orchestrator/verification/`):

| Лимит | Где применялся |
|---|---|
| 30000 мс | handshake-пробник моста (CQ1) |
| 60000 мс | обычные команды/сборка (`agent list`, `npm run build`/`check`) |
| 120000 мс | форс-прогоны V-RECURSION |
| 240000 мс | клиент V-LONG (фактически 211583 мс, Kill не понадобился) |
| 300000 мс | opencode-сессия V7 |

**Внешний лимит не отменяет внутренние таймауты и наоборот:**

- `mcp.orchestrator.timeout = 900000` в `opencode.json` — лимит хоста opencode
  на MCP-вызов; прежнее `15000` отсекало успешные длинные вызовы ошибкой
  **`-32001`** ещё до ответа моста (CQ1: `15000` в конфиге больше нет);
- `ORCH_TIMEOUT_MS`/`timeoutMs` моста (дефолт `900000`) — мост сам убивает
  дерево дочернего `opencode` (`taskkill /T /F`) и возвращает `success=false`;
- внешний таймаут защищает от зависания **самого процесса ожидания**
  (проверяющего/скрипта), который ни один из вышеперечисленных лимитов не
  покрывает: если мост, хост или дочерний процесс зависнут, без внешнего
  `WaitForExit(ms)+Kill`/`timeout` вызов не вернётся никогда.

Требование относится ко всем длинным вызовам схемы: прогоны `opencode run`
(V7/V-RECURSION), клиенты JSON-RPC (V-LONG/handshake) и любые будущие скрипты
верификации.

## Известные ограничения и риски

1. **Таймаут на долгих задачах.** Вызов синхронный: архитектор ждёт ответа всё
   время выполнения. Длинные задачи упираются в таймауты (блок `timeout: 900000`
   в `opencode.json`, `ORCH_TIMEOUT_MS`/`timeoutMs` моста). **Проверено (V-LONG,
   07.10.2026):** задача с тремя отдельными `Start-Sleep -Seconds 20` прошла за
   `callMs=211281` мс (`success=true`, `exitCode=0`) **без `-32001`**; клиентский
   лимит 240000 мс не достигнут (211583 мс). На практике предел (900000 мс)
   не отрабатывался — при его достижении мост убивает дерево дочернего процесса
   и возвращает `success=false`. Лечить декомпозицией задач на короткие.
   **Асинхронный режим submit/poll (отправить задачу → опросить статус) не
   реализован — остаётся открытым.**
2. **Стоимость.** Каждый вызов — отдельный headless `opencode run` со своей
   моделью и контекстом; делегирование мелочи поштучно дороже, чем одна
   интерактивная сессия.
3. **`ask` в headless не о чём спросить.** Попытка оркестратора сделать
   `git push`/`rm -rf` (permission `ask`) вернёт отказ, а не вопрос —
   запрошенное действие не выполнится.
4. **T2 не интерактивен** — только чтение лога (см. «Честное ограничение»
   выше); вмешаться в ход задачи из T2 нельзя.
5. **`files_changed` не видит файлы внутри неотслеживаемых каталогов:**
   `gitPorcelain()` использует `git status --porcelain` без `-uall`, поэтому git
   схлопывает, например, весь неотслеживаемый `tools/` в одну строку — новые
   файлы внутри такого каталога в дельте не видны (зафиксировано в отчёте
   проверки, фикс: `--untracked-files=all`).
6. **Параллельные вызовы сериализуются мьютексом:** второй независимый вызов в
   момент занятости отклоняется — архитектору нужно дождаться первого и
   повторить, а не рассчитывать на фактический параллелизм.
