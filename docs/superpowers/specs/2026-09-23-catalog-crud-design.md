# Справочник номенклатуры — CRUD каталога (дизайн)

Дата: 23.09.2026. Контур: `main` (Node/Express + EJS + Prisma + PostgreSQL).
Статус: утверждён в диалоге, перед реализацией.

## 1. Цель

Дать мастеру и администратору вести номенклатуру (`Catalog`) напрямую из
приложения: создавать, редактировать и удалять позиции, не дожидаясь обновления
Excel-файла. В перспективе Excel становится резервной копией, а источник правды —
БД + UI (отдельный шаг — перевод импорта на merge).

Сейчас в `Catalog` нет ни одного write-эндпоинта в UI-контурах: таблица
заполняется только импортом Excel (`server/scripts/import-excel.ts`, атомарная
замена), VBA `POST /api/vba/ingest` `uploadCatalog` (upsert новых кодов) и сидом
(только при пустой таблице). Запуск ссылается на `Catalog.partCode` (FK) — без
записи позиции мастер не может создать запуск на новое изделие.

## 2. Бэкенд — `server/src/routes/catalog.routes.ts`

Все новые эндпоинты — под `requireAuth('master')` (admin проходит любой фильтр
как superuser; shift/operator/otk → 403). Существующие GET-эндпоинты
(`GET /`, `GET /:code`, `GET /tree/units`) не меняются.

### 2.1. `POST /api/catalog` — создать позицию

- Тело — поля модели `Catalog` (канон — `server/prisma/schema.prisma:54`).
- Валидация: `code` обязателен и непустой после `trim()`; числовые поля —
  через `roundSmart` (`server/src/lib/round.ts`); флаги обработок — булевы.
- Дубль кода (PK `code`) → P2002 → **409** `{ error: 'Код уже существует' }`.
- Ответ: созданная запись (201).

### 2.2. `PUT /api/catalog/:code` — редактирование

- Без смены кода: обновление полей (та же валидация, что и POST).
- **Смена кода:** в теле передан `code`, отличный от `:code`:
  1. Проверить, что новый код свободен (иначе 409).
  2. В одной транзакции:
     - создать запись с новым кодом (копия остальных полей из текущего состояния);
     - каскадно переехать ссылки: `Launches.partCode`, `WorkOrders.partCode`,
       `PrintQueue.partCode`, `Queue.code` (все записи, ссылающиеся на старый код);
     - удалить старую запись.
  3. Ответ: обновлённая запись + `codeChanged: true` +
     `moved: { launches, workOrders, printQueue, queue }` — UI показывает
     предупреждение о числе изменённых ссылок.

### 2.3. `DELETE /api/catalog/:code` — удаление

- Если на код ссылается хотя бы одна запись `Launches`/`WorkOrders`/
  `PrintQueue`/`Queue` → **409** `{ error: 'Код используется', refs: {...} }`
  (кол-ва по каждой таблице). UI показывает перечень.
- Иначе — удаление (200).

## 3. UI

### 3.1. `/master` — вкладка «Номенклатура» становится редактором

- Поверх дерева — тулбар: поиск (по коду/наименованию/обозначению, через
  `GET /api/catalog?search=`) + кнопка «+ Добавить позицию».
- У каждого листа дерева — по наведению кнопки «✎» (редактировать) и «🗑»
  (удалить); клик по листу также открывает форму. Метрики
  (запуски/в работе/закрыто) и сворачивание дерева сохраняются.
- Модалка добавления/редактирования = полный набор полей модели: код,
  наименование, обозначение, обозначение(пред.), кол-во на родителя,
  тех-параметры (тип заготовки, материал, марка, размер заготовки, толщина
  стенки, длина резки, масса заготовки/детали) + флаги обработок (ТО, покрытие,
  резка/плазма/токарная/фрезерная/сверлильная/слесарная/гибка).
- Смена кода при редактировании → `confirm` «Код будет изменён, ссылки
  запусков/нарядов будут обновлены»; после сохранения показать `toast` с числом
  ссылок из `moved`.
- Удаление → `confirm`; при 409 показать перечень ссылок из ответа.

### 3.2. `/admin` — второй таб «Номенклатура»

- В топ-бар `admin.ejs` добавляется пункт «Номенклатура» рядом с «Сотрудники».
- Контент монтирует общий компонент (тот же, что и в `/master`).

### 3.3. Общий JS-компонент `server/src/public/catalog-manager.js`

- `mountCatalogManager(containerEl)` — дерево + поиск + плоская таблица + форма +
  обращения к `/api/catalog`, `/api/catalog/:code`.
- Стили — в `server/src/public/styles.css`, переиспользуя токены `.tree-*`.
- Подключение: `master-app.ejs` и `admin.ejs` добавляют `<script src="/catalog-manager.js">`
  (после `ui.js`; стиль подключается через существующий `styles.css`).

## 4. Правила / инварианты

- Код — единственный идентификатор (PK); дубли невозможны.
- Смена кода безопасна: все FK-ссылки переезжают в транзакции; ни один запуск/наряд
  не повисает с «мёртвым» `partCode`.
- Удаление позиции с любыми ссылками запрещено (409) — орфан-ссылок не создаётся.
- Числа округляются единым `roundSmart` при сохранении (как во всём приложении).

## 5. Взаимодействие с импортом Excel

На этом этапе `npm run import:excel` не меняется. Зафиксировано известное
ограничение: полный импорт выполняет атомарную замену (`deleteMany` + `createMany`),
поэтому при переимпорте вручную добавленные позиции могут быть потеряны.
Перевод импорта на merge (upsert без `deleteMany`, «Excel = резерв») — отдельный
шаг дорожки.

## 6. Дорожка

1. **Скелет:** эндпоинты POST/PUT/DELETE + компонент `catalog-manager.js` +
   интеграция в вкладку `/master` и таб `/admin` + форма поле-в-поле.
2. **Логика:** валидации, `roundSmart`, каскад смены кода с предупреждениями,
   защита удаления от ссылок.
3. **Автозаполнение** (детали обговариваются после шагов 1–2).

## 7. Проверки (Definition of Done)

- `cd server && npm run build` + `npm run check` — PASS.
- API-smoke против стенда: create 201; дубль кода 409; `code` пустой 400;
  смена кода → `codeChanged: true` + `moved` с корректными счётчиками; delete
  занятого кода → 409; delete свободного → 200; shift → 403.
- UI-probe: добавление через форму в `/master` (позиция видна в дереве),
  редактирование, смена кода с предупреждением, удаление; таб `/admin` работает
  тем же компонентом; консоль браузера без ошибок.
- Чистота стенда: тестовые коды (`TST-*`) удаляются SQL-cleanup в FK-порядке;
  живой каталог (2208 позиций) и рабочие запуски/наряды не тронуты.
- `docs/specs/data-model.md` (Catalog) актуализирован, если меняется описание
  способов заполнения.
