# Справочники каталога + автогенерация кода (дизайн)

Дата: 25.09.2026. Контур: `main` (Node/Express + EJS + Prisma + PostgreSQL).
Статус: утверждён в диалоге, перед реализацией.

## 1. Цель

После CRUD каталога (Этап 16) запись номенклатуры в `Catalog` полностью
свободна: «заготовку» можно завести как угодно, а код (`code`) вводится руками.
Этап делает запись **управляемой и структурной**:

1. **Справочники** — 5 полей записи переводятся из свободного текста в
   словари (при выборе + серверная валидация): `blankType`, `material`,
   `materialGrade`, `blankSize`, `priority`.
2. **Автогенерация кода** — код новой позиции система формирует из места в
   дереве (выбор родителя), руками код не вводится (исключение — admin для
   импорта/миграции/легаси).
3. **Чистка данных** — существующие 2208 позиций приводятся к эталону скриптом:
   мусор (`#N/A`, `0`, `—`, числа) → пусто («не задано»), коды позиций **не
   меняются** (ссылки запусков/нарядов не затрагиваются).

Текущее состояние данных (стенд `digital_narad`, Catalog=2208):
- `blankType` — 11 уникальных, 1712 пусто, мусор `0/—/1823`;
- `material` — 9 уникальных (Сталь 1543), мусор `0/0.6/68.47/—`, 624 пусто;
- `materialGrade` — 69 уникальных, из них 105 = `#N/A`, пусто 521;
- `blankSize` — 97 разных форматов, пусто 741;
- `priority`, `ppb` — пусто во **всех** строках.
Топ-уровень кодов — числа `1..22`; глубина 1–8 сегментов; 4583 пары «код —
префикс другого кода» (узел дерева одновременно деталь и родитель).

## 2. Ключевые решения (из диалога)

- **Код** — авто из дерева: `max (прямые дети) + 1`, удалённые номера не
  переиспользуются (код = стабильная идентичность), разделитель «/», top-уровень
  `max(1..22)+1 → 23`. Ручной ввод — только admin (импорт/миграция/легаси).
- **Узел дерева = реальная позиция** (без «папок»-групп): группировка — следствие
  кода. При создании под узлом, у которого нет строки в `Catalog` (узел существует
  только как префикс), сервер **материализует «родительские строки-контейнеры»**
  по пути (код + имя, техданные пустые) — полноценные позиции, доукомплектовываются
  позже.
- **«Не задано» = пустая строка** в БД, в UI отображается «—». Отдельных значений-
  заглушек в словарях нет.
- **Справочники** — пять полей; ведение: quick-add — master/admin (быстрая «+» в
  модалке), редактирование/деактивация/синонимы — только admin (таб «Справочники»
  в `/admin`).
- **Excel/VBA-ингест** — нормировка через синонимы; неизвестные значения
  **автоматически добавляются в словарь** (Excel = источник, интеграция не
  рвётся); в отличие от строгого UI.

## 3. Модель `DictionaryValue`

`server/prisma/schema.prisma` — новая модель:

```prisma
model DictionaryValue {
  id        Int      @id @default(autoincrement())
  type      String
  value     String
  synonyms  String[]
  isActive  Boolean  @default(true)
  sort      Int      @default(0)

  @@unique([type, value])
  @@index([type])
}
```

- `type` — одно из `blankType | material | materialGrade | blankSize | priority`
  (константы `DICT_TYPES` в `server/src/lib/dict.ts`).
- `value` — каноническое значение (после нормализации: trim, collapse пробелов).
- `synonyms` — варианты, под которые маппятся данные импорта/миграции
  (`'#N/A'`, `'0'`, `'—'`), учитываются при `normalizeValue`.
- `isActive` — деактивированные значения не предлагаются в UI и не принимаются
  валидацией (существующие строки каталога не пересматриваются).
- `sort` — порядок в выпадающем списке (0 = алфавитный fallback).
- Миграция — `prisma migrate dev`. Сид базовых значений — `server/prisma/data/
  dictionaries.json` (при пустой таблице; в т.ч. `priority: высокий/средний/низкий`).

`Catalog` строки `blankType/material/materialGrade/blankSize/priority` **остаются
String** (без FK) — минимально инвазивно, миграция данных не трогает `code`.

## 4. Библиотека `server/src/lib/dict.ts`

- `DICT_TYPES` — типы справочников (массив + `as const`).
- `normalizeDictValue(v: unknown): string` — trim + collapse пробелов.
- `toCanonical(prisma, type, raw)`: пусто → `''` (валидно, «не задано»); иначе
  ищет активное значение по `normalizeDictValue`, затем по синонимам → возвращает
  канон; неизвестное → `null` (невалидно, 400).
- `resolveOrCreate(prisma, type, raw)`: для импорта — канон через синонимы, либо
  create нового активного значения (возвращает `{value, created}`).
- `listActive(type)` — активные значения, сортировка `sort, value`.

## 5. Миграция данных ✦ `server/scripts/normalize-catalog-dicts.ts`

`npm run dict:migrate` (уже есть `scripts/set-passwords.ts` как образец: грузит
`server/.env`, `DATABASE_URL` из env/параметров).

Функции:
- `--dry` — только отчёт, без записи; по умолчанию применяет.
- Идемпотентен (повторный запуск не создаёт дублей словаря, не трогает чистые
  строки).
- Эталоны (в скрипте как данные):
  - `blankType`: канон `[Круг, Труба, Лист, Литьё, Шестигранник, Поковка, Полоса]`;
    мусор `{'0','—','1823'}` и прочие не-эталоны → «».
  - `material`: канон `[Сталь, Бронза, Алюминий, Полиамид]`; мусор
    `{'0','0.6','68.47','—'}` → «».
  - `materialGrade`: канон — все реальные марки из данных (`09Г2С`, `40Х`, `20`,
    `45` …), кроме стоп-списка `{'#N/A','2997','3'}` и числовых → «».
  - `blankSize`: реальные типоразмеры; стоп-список `#N/A`, пустые, числовые-мусор → «».
  - `priority`: сид `высокий/средний/низкий`; из строк каталога не берётся.
- Алгоритм по каждому типу:
  1. собрать distinct из `Catalog`;
  2. для каждого: `normalizeDictValue` → синонимы/стоп → канон или «»;
  3. записать `DictionaryValue` (createMany, idempotent: upsert по `[type,value]`);
  4. `updateMany` по `Catalog` с маппингом старых значений на канон («» для мусора);
  5. отчёт (строк: значений→словарь, изменено полей, очищено, добавлено в словарь).
- `Catalog.code` не меняется ни при каких условиях.
- Запуск на **оба контура**: `MOSD` (dev `server/.env`) и стенд `digital_narad`
  (host-порт 5434, креды из `server/.env` `POSTGRES_*`).

## 6. Серверные эндпоинты (`server/src/routes/catalog.routes.ts` + новый
`server/src/routes/dictionaries.routes.ts`)

Все — под `requireAuth` (роль указана у каждого).

### 6.1. `POST /api/catalog/next-code` — предложить код
Body `{ parent?: string }` (код родителя или пусто). Ответ `{ code, wouldMaterialize: string[] }`.
- `next-code` — **чистое предложение, ничего не пишет**; `wouldMaterialize` —
  превью строк-контейнеров, которые будут созданы на `POST` (см. 2).
- Без `parent`: top = `max(числовые 1-е сегменты) + 1` (22 → 23).
- С `parent`: кандидат = `parent + '/' + (max числовой последний сегмент прямых
  детей родителя + 1)`; прямой ребёнок — код вида `parent + '/' + <число>` (один
  дополнительный сегмент). Если под родителем нет детей — номер `1`.
- Ошибки: непустой `parent`, не являющийся префиксом ни одного кода дерева → 400.

Фактическое создание — на `POST /api/catalog`: при `parent` (в теле), у которого
нет строки в `Catalog`, сервер сначала материализует строки-контейнеры по пути
(код + имя узла дерева/пусто, техданные пустые), затем создаёт позицию;
в ответ включается `materialized: string[]`.

### 6.2. Валидация словарей в POST/PUT `/api/catalog`
В `normalizeBody`/после неё: каждое из 5 полей — **пустое значение всегда валидно**
(остаётся пустой строкой «не задано»); непустое — обязано совпасть с активным
значением словаря своего типа (`toCanonical`) → иначе **400**
`{ error: 'Значение «<v>» не в пределах <label>', field }`. Значение на запись
сохраняется каноническим.
Код: сервер **пересчитывает кандидата сам** (не доверяет телу): для POST от master
принимается только `code`, равный `next-code` для переданного `parent` (с учётом
материализации контейнеров), либо набор кодов материализованных контейнеров;
иной `code` → 400 «Код позиции формируется автоматически». Оверрайд кода — только
admin (импорт/миграция/легаси). Для PUT без смены кода проверка не блокирует
(код остаётся прежним); смена кода на не-предложенный → 400 (admin исключён).

### 6.3. Новый `server/src/routes/dictionaries.routes.ts` (`/api/dictionaries`)
- `GET /:type` — активные значения `[{id, value, synonyms, isActive, sort}]`
  (`requireAuth('master')`; admin видит и неактивные через `?all=1`).
- `POST /:type` — quick-add: `{value}` (normalize; trim) → create активного
  значения; дубль → 409. (`requireAuth('master')`.)
- `PUT /:type/:id` — переименовать/синонимы/`sort` (значение уникально по типу →
  409 дубль). (`requireAuth('admin')`.)
- `POST /:type/:id/deactivate` — `isActive=false`. (`requireAuth('admin')`.)
  Деактивация не трогает существующие `Catalog`-строки; новое использование
  запрещено валидацией.

## 7. UI

### 7.1. Модалка `catalog-manager.js` («Добавить позицию»/«Редактировать»)
- Поле **«Родитель»**: выбор узла из дерева (сам дерево-компонент как навигатор
  или `<select>` со списком узлов дерева). При создании обязателен выбор либо
  «корень»; при выборе — кнопка «Сгенерировать код»/автоподстановка через
  `next-code`: строка «Код: `21.1/9/2` (сгенерирован системой)».
- Поле «Код»: read-only, значение от `next-code`; редактируется только у admin
  (переключатель «ручной ввод»).
- 5 словарных полей → `<select>` по `GET /api/dictionaries/:type` + кнопка «+»:
  inline quick-add (POST, валид → обновить select, выбрать новое).
- Пустое значение → вариант «— (не задано)» со значением пустой строки.
- Серверный 400 `{field}` → подстветка поля + тост «Значение не в словаре».
- «Не задано» в дереве/таблицах уже отображается пустой строкой; в UI показ «—».

### 7.2. `/admin` — таб «Справочники»
Навигация «Сотрудники | Номенклатура | **Справочники**». Список типов (5),
внутри — таблица значений: value, synonyms (ввод через запятую), активен,
сортировка; действия: добавить, переименовать, деактивировать. На общем
компоненте `public/dict-manager.js` (стиль `catalog-manager.js`).

### 7.3. Стили
`styles.css`: `.dict-*` (таблица значений, chips синонимов), `.cm-parent-sel`,
`select`-обёртки. Тёмная плашка-навигация `/admin` расширяется третьим табом.

## 8. Интеграция с импортом

### 8.1. `server/scripts/import-excel.ts`
После парсинга строк — нормализация 5 полей `resolveOrCreate` (синонимы → канон,
новые значения → create в словарь); в итоговый отчёт добавить счётчики
«значений добавлено в справочник по типу». Поведение атомарной замены каталога
не меняется.

### 8.2. `server/src/routes/vba.routes.ts` (`uploadCatalog`)
Перед `prisma.catalog.upsert` — те же `resolveOrCreate`; неизвестное значение
создаётся в словаре автоматически, в `created` возвращается поле `dictAdded`
(число). `update: {}` остаётся.

## 9. Тесты (E2E Playwright, `tests/e2e/test_dict_catalog.py`)

Креды через env (как `test_catalog_crud.py`). Независимые от живых данных
(создание/удаление тестовых словарей и позиций, cleanup в конце):

1. `next-code` топ-уровень (мастер) → 200, `code` = `23` (если свободен; обёрнуто).
2. `next-code` под родителем: создать тестовую позицию-родителя (ручной код через
   admin) → `next-code {parent}` = `parent/1`; после создания ребёнка следующий = `parent/2`.
3. Материализация: `next-code {parent: '99/9'}` (только префикс, без строки) →
   `materialized` непусто, затем создать ребёнка — путь существует.
4. POST `/api/catalog` без `code` от master (нет `next-code`) → 400.
5. POST с валидными словарными значениями → 201; невалидное `material` → 400 `{field}`.
6. quick-add словаря (master) → 201; дубль → 409; `GET /:type` содержит.
7. Деактивация (admin) → валидация значения → 400; деактивированное скрыто из `GET`.
8. Миграция: после прогона `dict:migrate` (dev-контур/стенд) — `#N/A`/мусора в
   словарных полях нет (в рамках тестовых значений), `Catalog.code` не изменились.
9. UI `/admin`: таб «Справочники» — select типа, список значений, добавление.
10. UI модалки мастера: селекты словарей + «+», строка «сгенерирован код».
11. Cleanup: тестовые позиции/значения удалены; `Catalog` 2208, стоп-значения не
    появились.

Регресс: `test_catalog_crud.py` 15/15, `test_admin.py` 5/5, `test_master.py`
12/12, `npm run build` + `npm run check` PASS.

## 10. Деплой и документы

- Миграция модели: `prisma migrate dev` (создать миграцию) + применить на стенде
  через `docker compose up -d --build` (`migrate deploy` на старте).
- Словари: сид (`npx prisma db seed` на стенде) + `npm run dict:migrate` на оба
  контура; `/health` → `{status:'ok', db:'connected'}`.
- Док: `docs/specs/dictionaries-catalog.md` (справочная), ADR (модель словарей +
  автокод), отчёт `docs/reports/2026-09-25-dictionaries-catalog.md`,
  актуализация `docs/reports/STATUS.md`; коммиты по логическим этапам + тег.
