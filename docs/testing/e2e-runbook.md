# Runbook: запуск E2E-тестирования «ЦифровойНаряд»

Проверенный алгоритм запуска E2E-прогонов по ролям. Применять после каждого
деплоя нового `modules/*.md` и при жалобах «пишет Загрузка…/пустая страница».

## Почему такой алгоритм (коротко)

Google-шлюз не пускает headless/автоматизированный браузер войти в Google и
пройти консент. Поэтому:

1. **Один раз** вручную (в реальном окне браузера) залогиниться в Google и
   пройти консент-экран Apps Script, а затем сохранить сессию.
2. Дальше **каждый прогон роли** идёт headless, но с этой сохранённой сессией.

Три главные грабли, на которых всё падало:
- Google блокирует встроенный chromium Playwright («браузер или приложение
  небезопасны») → используется `channel="chrome"` (реальный установленный
  браузер) + stealth-флаги.
- Приложение рендерится **внутри sandboxed-iframe** (`userCodeAppPanel`), а не
  в top-frame → селекторы ищутся по всем фреймам (frame-aware), `#login` и весь
  UI ролей искать в top-frame бессмысленно.
- Накапливающийся persistent-профиль давал автологин между ролями → каждый
  прогон идёт в **чистом контексте**, сеется только `storage_state.json`
  (Google-сессия), localStorage приложения пуст → форма логина стабильно видна.

## Структура

`tests/e2e/`:
- `config.py` — URL аппа, канал браузера, пути, учётные данные ролей
  (env-переопределяемые), карта лендингов.
- `helpers.py` — frame-aware селекторы, вход по форме, скриншоты, консент-детект.
- `runner.py` — общий прогон роли в чистом контексте + сводка PASS/FAIL
  (UTF-8-совместимый вывод, emoji не ломают cp1251-консоль).
- `session_setup.py` — одноразовая привязка авторизованной Google-сессии.
- `test_operator.py`, `test_otk.py`, `test_master.py`, `test_shift.py` — ролевые сценарии.
- `profile/`, `screenshots/` — артефакты, **в git не идут** (`.gitignore`).

## Шаг 1. Привязка сессии (один раз, не в фоне для основного входа)

Запустить **одним процессом** (не фоновым, если ещё не залогинены), чтобы видеть
окно браузера:

```powershell
cd <корень проекта>
python tests/e2e/session_setup.py
```

Откроется реальное окно Chrome на десктопе. Если не залогинены — войти в Google
(аккаунт, у которого есть доступ к таблице аппа), пройти консент-экран
«Это приложение создано пользователем Google Apps Script». Когда появится форма
входа приложения «ЦифровойНаряд» (Логин/Пароль), скрипт сам детектит её по всем
фреймам и сохраняет сессию в `tests/e2e/profile/storage_state.json`.

> Не переоткрывать апп во время Google-входа: вкладка временно уходит на
> `accounts.google.com`, повторное открытие аппа отменит логин.

По умолчанию таймаут ожидания — 420 c (env `ND_SESSION_TIMEOUT`, при необходимости
увеличить, напр. `$env:ND_SESSION_TIMEOUT="900"`).

## Шаг 2. Прогон ролей

Проверяется: вход по форме → URL полной страницы → UI отрисован (текст из
фреймов) → **F5 не возвращает форму входа** → (оператор) 4 вкладки.

```powershell
python tests/e2e/test_operator.py
python tests/e2e/test_otk.py
python tests/e2e/test_master.py
python tests/e2e/test_shift.py
```

Каждый тест выводит `[PASS]/[FAIL]` и в конце сводку; код выхода `0` — все
прошли, `1` — есть падения. Скриншоты плюс лог консоли — в `screenshots/`.

Ожидаемые результаты (см. отчёт `docs/reports/2026-09-04-e2e-roles.md`):
operator **6/6**, otk **4/4**, master **4/4**, shift **4/4**.

## Шаг 3. Переопределение данных при необходимости

- URL: `$env:ND_APP_URL="<...>"`.
- Канал браузера: `$env:ND_BROWSER_CHANNEL="chrome"` (по умолчанию `chrome`; можно
  `msedge`).
- Учётные данные роли (иначе fallback на тестовые operator/123 и т.п.):
  `$env:ND_LOGIN_OPERATOR`, `$env:ND_PASSWORD_OPERATOR`, `$env:ND_NAME_OPERATOR`
  (аналогично `_OTK/_MASTER/_SHIFT`).

## Когда прогонять

- После ручного деплоя нового `modules/*.md` (см. `.opencode/skills/digitalapps-deploy`).
- При «Загрузка…»/пустой странице — это первая диагностика (`docs/МАСТЕР-ДИАГНОСТИКА.md`).
- При точечном изменении `Auth.md`/`OperatorUI.md`/`ShiftUI.md`/`OtkUI.md` — минимум
  затронутая роль, желательно все 4 (refresh-чеки ловят регрессии авторизации).

## Дальнейшее развитие

Текущие сценарии покрывают вход + рендер + редирект + refresh. Полный
бизнес-цикл (shift выдаёт наряд → оператор → ОТК → закрытие/доработка) ещё не
автоматизирован — на заметку для следующего этапа.
