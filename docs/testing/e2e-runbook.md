# Runbook: запуск E2E-тестирования «ЦифровойНаряд» (new-стек)

Проверенный алгоритм запуска E2E-прогонов по ролям. Применять после каждого
деплоя (Docker) и при жалобах «пишет Загрузка…/пустая страница».

> Статус: харнесс `tests/e2e/` адаптирован под новый стек (JWT-логин через
> `/login`, full-page E2E без Google-сессии/фреймов). Прогон ролей — 26/26 PASS
> (master дополнительно проверяет вкладки Сводка/Планирование/Номенклатура/Отчёты).
> Полный бизнес-цикл — `test_bizcycle.py` 37/37 PASS. Исторический GAS-харнесс
> (против `/exec`) живёт в ветке `google-apps`.

## Почему новый алгоритм (коротко)

Google-шлюз и sandboxed-iframe остались в прошлом:

1. Новый стек — обычный веб-сервер на `localhost:3000` (JWT внутри `localStorage`).
   **Никакой Google-сессии не нужно** — каждый прогон логинится по форме `/login`
   (bcrypt-сверка, `POST /api/login` → access+refresh токены).
2. Приложение рендерит **полную страницу** (EJS), а не sandboxed-iframe →
   селекторы — обычные запросы к top-frame, `#login` и весь UI ищутся напрямую.
3. Чистый контекст на прогон (как и раньше, `storage_state.json` уходит в прошлое)
   — localStorage приложения пуст → форма логина стабильно видна.

## Структура (целевая)

`tests/e2e/`:
- `config.py` — `APP_URL=http://localhost:3000`, учётные данные ролей из сида
  (env-переопределяемые `ND_LOGIN_*`, `ND_PASSWORD_*`, `ND_NAME_*`), карта лендингов.
- `helpers.py` — вход по форме `/login`, скриншоты, ожидания.
- `runner.py` — общий прогон роли в чистом контексте + сводка PASS/FAIL.
- `test_operator.py`, `test_otk.py`, `test_master.py`, `test_shift.py` — ролевые сценарии.
- `screenshots/`, `.secrets/` — артефакты, **в git не идут** (`.gitignore`).

GAS-специфика (Google-сессия, фреймы, `session_setup.py`, `flows.py`, seed-хелперы)
перенесена в ветку `google-apps`.

## Шаг 1. Подъём стека

```powershell
cd server
npm ci
# server/.env — из server/.env.example (DATABASE_URL=…@localhost:5432/MOSD)
npm run db:migrate
npm run db:seed
npm run dev
```

Smoke: `GET http://localhost:3000/health` → `{status:'ok', db:'ok'}`.

## Шаг 2. Прогон ролей

Проверяется: вход по форме `/login` → страница роли отрисована (текст из
top-frame) → **F5 не возвращает форму входа** → (оператор) вкладки.

```powershell
cd <корень проекта>
python tests/e2e/test_operator.py
python tests/e2e/test_otk.py
python tests/e2e/test_master.py
python tests/e2e/test_shift.py
```

Каждый тест выводит `[PASS]/[FAIL]` и сводку; код выхода `0` — все прошли,
`1` — есть падения. Скриншоты плюс лог консоли — в `screenshots/`.

Ожидаемые результаты: operator **6/6**, otk **4/4**, master **12/12** (вход,
рендер, refresh, 4 вкладки×2), shift **4/4** (эталон 26/26).

## Шаг 2.1. Полный бизнес-цикл (роли together)

`tests/e2e/test_bizcycle.py` — сквозной прогон всего производственного потока
через UI всех четырёх ролей против стенда:

```
master  → 2 запуска (Гидробак, qty 10/20, ПА E2E-71/E2E-72)
operator→ открывает смену на Т1-1 (нужна для выдачи)
shift   → выдаёт 2 наряда (Т1-1 / Т1-2)
operator→ happy: оба наряда в работу + переходы → waiting_otk
otk     → наряд №1: проверить переход + закрыть; наряд №2: на доработку
operator→ rework: правка №2 (новый переход) → waiting_otk
otk     → проверка + закрытие №2; очередь пуста
master  → аналитика: Сводка/Номенклатура/Отчёты отражают данные
cleanup → SQL-зачистка тестовых нарядов/запусков/смены (FK-порядок)
```

```powershell
python tests/e2e/test_bizcycle.py
```

Эталон — **37/37 PASS**; тест сам удаляет свои данные (стенд остаётся чистым,
каталог 2208 и «живые» смены пользователя не трогаются). Требуется запущенный
Docker-контейнер `server-db-1` (cleanup ходит в БД через `docker exec psql`).

Особенности реализации (грабли, уже пройденные):
- `wait_for_selector` по умолчанию `state="visible"` — для `<option>` внутри
  закрытого `<select>` ждать сам `<select>`, затем `page.select_option`.
- Строку наряда искать **точным** совпадением первой ячейки
  (`naryad_row()`), а не `has_text=<номер>`: при коллизии секунды ID получает
  суффикс `-2`, и подстрока совпала бы с двумя строками.
- Заголовки таблиц в аналитике рендерятся `text-transform: uppercase` →
  проверять «ЗАКРЫТО НАРЯДОВ», не «Закрыто нарядов».
- Смена открывается на Т1-1 в начале и удаляется в cleanup (`Shifts`).

## Шаг 3. Переопределение данных при необходимости

- URL: `$env:ND_APP_URL="http://localhost:3000"`.
- Учётные данные роли (fallback — сид: логины `master`/`operator`/`otk`/`shift`,
  пароль `123`):
  `$env:ND_LOGIN_OPERATOR`, `$env:ND_PASSWORD_OPERATOR`, `$env:ND_NAME_OPERATOR`
  (аналогично `_OTK/_MASTER/_SHIFT`).

## Когда прогонять

- После деплоя (Docker) или значимых правок сервера/вью.
- При «Загрузка…»/пустой странице — быстрая диагностика через `/health` и API-логи.
- При точечном изменении авторизации/вью роли — минимум затронутая роль, желательно все 4.

## Дальнейшее развитие

Ролевые сценарии покрывают вход + рендер + re-логин; полный бизнес-цикл (запуск →
выдача → оператор → ОТК → rework → закрытие → аналитика) автоматизирован в
`test_bizcycle.py`. Дальше — вынести в харнесс кейсы «закрытая смена в истории»,
«уведомления» (бейдж/тост/dropdown) и содержимое вкладок/графиков аналитики мастера.
