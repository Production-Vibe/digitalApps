# Runbook: запуск E2E-тестирования «ЦифровойНаряд» (new-стек)

Проверенный алгоритм запуска E2E-прогонов по ролям. Применять после каждого
деплоя (Docker) и при жалобах «пишет Загрузка…/пустая страница».

> Статус: харнесс `tests/e2e/` адаптирован под новый стек (JWT-логин через
> `/login`, full-page E2E без Google-сессии/фреймов). Прогон ролей — **31/31 PASS**
> (admin 5, operator 6, otk 4, master 12, shift 4; master проверяет вкладки
> Сводка/Создать запуск/Номенклатура/Период). Полный бизнес-цикл —
> `test_bizcycle.py` 51/51 PASS; авторизация/регистрация/защита/деактивация —
> `test_auth_flow.py` 33/33 PASS. Исторический GAS-харнесс (против `/exec`)
> живёт в ветке `google-apps`.

## Почему новый алгоритм (коротко)

Google-шлюз и sandboxed-iframe остались в прошлом:

1. Новый стек — обычный веб-сервер на `localhost:3000` (JWT внутри `localStorage`).
   **Никакой Google-сессии не нужно** — каждый прогон логинится по форме `/login`
   (bcrypt-сверка, `POST /api/login` → access+refresh токены).
2. Приложение рендерит **полную страницу** (EJS), а не sandboxed-iframe →
   селекторы — обычные запросы к top-frame, `#login` и весь UI ищутся напрямую.
3. Чистый контекст на прогон (как и раньше, `storage_state.json` уходит в прошлое)
   — localStorage приложения пуст → форма логина стабильно видна.

## Структура (целевая)

`tests/e2e/`:
- `config.py` — `APP_URL=http://localhost:3000`, учётные данные ролей из сида
  (env-переопределяемые `ND_LOGIN_*`, `ND_PASSWORD_*`, `ND_NAME_*`), карта лендингов.
- `helpers.py` — вход по форме `/login`, скриншоты, ожидания.
- `runner.py` — общий прогон роли в чистом контексте + сводка PASS/FAIL.
- `test_admin.py`, `test_operator.py`, `test_otk.py`, `test_master.py`,
  `test_shift.py` — ролевые сценарии.
- `test_auth_flow.py` — авторизация/регистрация/защита входа/деактивация
  (API через Playwright `APIRequestContext` + UI-таб «Регистрация»).
- `screenshots/`, `.secrets/` — артефакты, **в git не идут** (`.gitignore`).

GAS-специфика (Google-сессия, фреймы, `session_setup.py`, `flows.py`, seed-хелперы)
перенесена в ветку `google-apps`.

## Шаг 2.1. Полный бизнес-цикл (роли together)

`tests/e2e/test_bizcycle.py` — сквозной прогон всего производственного потока
через UI всех четырёх ролей против стенда:

```
master  → 2 запуска (Гидробак, qty 10/20, ПА E2E-71/E2E-72)
operator→ открывает смену на Т1-1 (нужна для выдачи)
shift   → выдаёт 2 наряда (Т1-1 / Т1-2)
operator→ happy: оба наряда в работу + переходы → waiting_otk
operator→ уведомления: колокольчик + бейдж непрочитанных + dropdown + mark-read
otk     → наряд №1: проверить переход + закрыть; наряд №2: на доработку
operator→ (listener-сессия ждёт) тост уведомления о доработке
operator→ rework: правка №2 (новый переход) → waiting_otk
otk     → проверка + закрытие №2; очередь пуста
master  → аналитика: Сводка/Номенклатура/Отчёты (графики + таблицы) с данными
operator→ закрывает init-смену: форма открытия видна + история смен (Закрыта)
cleanup → SQL-зачистка тестовых нарядов/запусков/смены (FK-порядок)
```

```powershell
python tests/e2e/test_bizcycle.py
```

Эталон — **51/51 PASS**; тест сам удаляет свои данные (стенд остаётся чистым,
каталог 2208 и «живые» смены/запуски пользователя не трогаются). Требуется
запущенный Docker-контейнер `server-db-1` (cleanup ходит в БД через
`docker exec psql`).

Особенности реализации (грабли, уже пройденные):
- `wait_for_selector` по умолчанию `state="visible"` — для `<option>` внутри
  закрытого `<select>` ждать сам `<select>`, затем `page.select_option`.
- Строку наряда/смены искать **точным** совпадением первой ячейки
  (`row_by_first_cell()`), а не `has_text=<номер>`: при коллизии секунды ID
  получает суффикс `-2`, и подстрока совпала бы с двумя строками.
- Заголовки таблиц в аналитике рендерятся `text-transform: uppercase` →
  проверять «ЗАКРЫТО НАРЯДОВ», не «Закрыто нарядов».
- Панель уведомлений сначала рендерит пусто, затем заполняется асинхронно →
  ждать появления `.notif__item`, а не сразу после открытия.
- Заголовок уведомления о выдаче — «Новый наряд» (не «Наряд выдан») → искать
  «наряд» без учёта регистра.
- Тост от уведомления приходит на 15-секундном поллинге (ждём до ~30 с) и его
  нельзя путать с тостом собственного действия оператора («Переход записан») —
  `operator_wait_toast()` фильтрует по ключевым словам (наряд/закрыт/доработк).
- Смена открывается на Т1-1 в начале и закрывается в конце (проверка истории),
  удаляется в cleanup (`Shifts`); закрывается строго по своему `id`.
- «Живые» данные пользователя (свои запуски/смены/уведомления) остаются —
  cleanup трогает только тестовые ID.
- После перехода на `/api/session` (этап 13) страницы ролей рендерят контент
  **асинхронно** (`initSession()` → затем `loadAll()/loadQueue()/…`): заголовок
  «Наряды в работе»/«Смены» появляется с задержкой ~0.2 с. Проверки входа должны
  использовать `wait_text()`/`wait_selector()`, а не мгновенный
  `page.inner_text('body')` (иначе false-negative «вход (rework)»).

## Шаг 2.2. Авторизация / регистрация / защита входа / деактивация

`tests/e2e/test_auth_flow.py` — проверка цепочки auth после смены боевых паролей
(API через Playwright `APIRequestContext` + один UI-кейс формы регистрации):

```
АВТОРИЗАЦИЯ: вход 5 боевых ролей новым паролем (200+токен), кука nd_refresh,
  123 → 401, refresh/session/logout (401 после logout), /me (bearer).
РЕГИСТРАЦИЯ: role в теле игнорируется → operator, авто-вход, дубль 409,
  валидации 400 (пустой/длинный логин, ФИО одним словом, пароль <6, mismatch);
  UI: таб «Регистрация» → /operator → «Выйти» → /login.
ЗАЩИТА ВХОДА: 5 неудач на тестовом логине → 401, 6-я попытка → 429 (блок 15 мин).
ДЕАКТИВАЦИЯ: admin выключает тестового оператора → вход 403, session/refresh 401,
  скрыт из /api/employees, реактивация → 200, сам-отключение admin → 400.
CLEANUP: тестовые операторы удаляются SQL-ом (docker exec).
```

```powershell
. tests/e2e/.secrets/e2e-env.ps1
python tests/e2e/test_auth_flow.py
```

Эталон — **33/33 PASS**. Примечания: throttle-блок ложится только на
синтетический логин `nobody-probe` (in-memory, истекает за 15 мин) и не задевает
боевые роли; тестовые логины `op_probe_*`/`op_ui_*` снабжаются случайным
суффиксом (повторные прогоны в ту же минуту безопасны) и удаляются в cleanup.
`APIRequestContext` — `request.fetch(url, method=…)` (никак не `request.request`).

## Шаг 3. Переопределение данных при необходимости

- URL: `$env:ND_APP_URL="http://localhost:3000"`.
- Учётные данные роли: `tests/e2e/.secrets/e2e-env.ps1` (gitignored) — боёвые
  логины/пароли/ФИО всех ролей (`ND_LOGIN_*`, `ND_PASSWORD_*`, `ND_NAME_*`, вкл.
  `_ADMIN`). Загрузка перед прогоном:

  ```powershell
  . tests/e2e/.secrets/e2e-env.ps1
  ```

  > **Важно:** `config.py._cred()` срабатывает только когда заданы **и**
  > `ND_LOGIN_<ROLE>`, **и** `ND_PASSWORD_<ROLE>` вместе (пары login+password).
  > Если задать только пароль — fallback на сидовый `123` (неверен на боевом
  > стенде → «Неверный логин или пароль»). Пример файла — в `e2e-env.ps1`.
  > Fallback `123` в коде остаётся только для пустого/дев-стенда.

## Когда прогонять

- После деплоя (Docker) или значимых правок сервера/вью.
- При «Загрузка…»/пустой странице — быстрая диагностика через `/health` и API-логи.
- При точечном изменении авторизации/вью роли — минимум затронутая роль, желательно все 4.
