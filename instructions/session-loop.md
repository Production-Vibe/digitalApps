# Session-loop — протокол цикла handoff/restart

Длинная задача живёт не в одной сессии, а в цикле: исполнение → handoff →
restart → исполнение. Этот файл — контракт цикла: когда записывать бриф, в каком
он формате, как продолжать работу после рестарта, как останавливаться и как
драйвер читает состояние. Формат брифа — `.opencode/commands/handoff.md`; ритуал
авто-чтения — пункт 0 «при старте» в `AGENTS.md`; брифы — `.opencode/handoff/`
(gitignored).

## Триггер handoff

- **Контекст ≥ ~55–60%** (напоминание плагина) — записывай бриф, не дожидаясь
  компакшена.
- **Граница фазы/группы** — завершилась утверждённая группа работ — тоже
  триггер, даже если контекст мал.
- На триггере: `/handoff <для чего следующая сессия>` → бриф в
  `.opencode/handoff/handoff-<yyMMdd-HHmmss>.md`, затем ход завершается
  (см. «Семантика остановки»).

## Frontmatter (машиночитаемый)

В начале брифа — YAML-frontmatter с полями цикла:

- `loop: continue|done|blocked` — цикл продолжается / цикл завершён /
  нужен вопрос или решение пользователя;
- `iteration: <int>` — номер итерации цикла (с каждой новой сессией +1);
- `approved_plan: <ref>` — ссылка на утверждённый план (путь в `docs/specs/`,
  `.opencode/design/` или отчёте этапа);
- `session_config: <path>` — путь к конфигу преднастроек сессии (обычно
  `.opencode/session/config.json`, см. `instructions/session-bootstrap.md`);
- `next_action: <short>` — одно конкретное действие для следующей сессии.

Далее — человекочитаемая «живая нить» по формату `/handoff`: что в работе и
почему, следующий шаг, предложенные скиллы; ссылки вместо копий, допущения
помечены, секреты вырезаны.

## Resume-режим (старт с продолжением)

Свежий handoff валиден, когда это самый поздний файл в `.opencode/handoff/` и
его состояние не противоречит `STATUS.md`/`git log` (пункт 0 ритуала старта в
`AGENTS.md`). Если он валиден и в нём `loop: continue` — сессия стартует в
resume-режиме:

- это продолжение фазы исполнения по **уже утверждённому** плану
  (`approved_plan`) — pre-approval уже пройден, работа идёт сразу с
  `next_action`;
- преднастройки **наследуются**: конфиг из `session_config` брифа показывается
  как «подтвердить/изменить», полный опрос не проводится
  (`instructions/session-bootstrap.md`, resume-ветка);
- работать только в утверждённом scope: план не пересматривается, объём не
  расширяется;
- любая задача вне scope — стоп: записать handoff с `loop: blocked` и задать
  вопрос пользователю, продолжение — только после его ответа.

## Семантика остановки

Остановка (контекст на пределе, конец фазы, вопрос пользователю, `blocked`)
означает одно: **записать handoff с актуальным frontmatter и завершить ход**.
Ход без записанного брифа теряет нить — следующая сессия стартует с нуля.

## Контракт драйвера

Драйвер читает **frontmatter свежего handoff** и **`.opencode/loop/state.json`**
(машинное состояние цикла: итерация, текущая фаза, `approved_plan`; файл ведёт
драйвер). По ним решается, resume это или холодный старт: `loop: continue` при
согласованных источниках → resume-режим; `done` → цикл закрыт; `blocked` → ход
за пользователем; расхождение или отсутствие данных → холодный старт с полного
pre-approval.
