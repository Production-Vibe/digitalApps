# Верификация MCP-моста `tools/mcp-orchestrator` (контрольная точка T2)

Дата: 06.10.2026. Проверяющий: роль Tester (делегированная верификация t1-bridge).
Объект: `tools/mcp-orchestrator/{index.mjs,package.json,watch.ps1,.gitignore}` (+ `node_modules/`, `logs/`).
Код моста **не редактировался**. Временные пробники создавались в
`tools/mcp-orchestrator/.probe/` и **удалены** по завершении (каталога `.probe/` больше нет).

Способ прогона: два временных пробника, написанных для этой проверки, поднимали мост как
дочерний процесс `node index.mjs` с `stdio: pipe` и гоняли raw JSON-RPC вручную:

```js
spawn(process.execPath, ["…/tools/mcp-orchestrator/index.mjs"],
      { cwd: "C:/Projects/digitalApps", env: { ...process.env, ORCH_AGENT: "" } })
```

`ORCH_AGENT=""` — агента `orchestrator` в этой фазе ещё нет (создаётся следующей группой);
мост это поддерживает: пустой `ORCH_AGENT` → в `spawn` не добавляется `--agent`
(в логе: `spawn: …opencode.exe "run" "--format" "json" <промпт 238 симв.>` — без `--agent`).

Дочерний процесс реально работал с файлом (из `stdout` и из лога): `tool| write` →

**Ограничение/наблюдение по `files_changed`:** значение `[]`, а не `[t2.txt]`. Причина —
`gitPorcelain()` использует `git status --porcelain` **без `-uall`**, и git схлопывает весь
неотслеживаемый каталог `tools/` в одну строку `?? tools/` (она одинакова до и после), поэтому
новый файл внутри невидим для `diffPorcelain`. Доказательство:

```
$ git status --porcelain            →  ?? tools/
$ git status --porcelain -uall      →  ?? tools/mcp-orchestrator/.probe/t2.txt   (и ещё 4 файла моста)
```

Сам акцепт V3a не пострадал: файл проверен напрямую через `fs`. Рекомендация для t1 (не
исправлялось здесь, код моста не редактировался): в `index.mjs:gitPorcelain()` брать
`["status","--porcelain","--untracked-files=all"]`.

## Наблюдения (не блокеры; исправление — на стороне t1)

1. **`files_changed` не видит файлы внутри неотслеживаемого каталога** — `gitPorcelain()` без
   `-uall` (см. §2). Фикс: `git status --porcelain --untracked-files=all` в `index.mjs`.
2. **`final-smoke.mjs` исчез** из `tools/mcp-orchestrator/` в течение сессии (был в первом
   `Get-ChildItem`, позже отсутствовал), `probe1.mjs` из заявленных артефактов t1 отсутствовал
   с самого начала. Удалял их **не** верификатор (мои команды создавали и удаляли только
   `.probe/`); вероятно, финальная уборка со стороны t1 шла параллельно. На акцепты не влияет.
3. В логе остались записи предыдущих прогонов t1 (в т.ч.
   `=== Задача #1: старт … агент orchestrator …` → `success=true, код=0, 11006 мс` со
   `spawn: … "run" "--format" "json" "--agent" "orchestrator"`): на живом opencode несуществующий
   `--agent` не валит процесс с ненулевым кодом. Это запись чужого прогона, не мой — факт
   приведён как есть, без интерпретации.
4. Ограничение фазы: агента `orchestrator` в `.opencode/agents/` сейчас нет (только `e2e.md`),
   живой прогон сделан с `ORCH_AGENT=""` (мост поддерживает пустое значение → без `--agent`),
   дефолтный встроенный агент отработал штатно. Проверка с реальным агентом `orchestrator`
   возможна только после его создания (следующая группа).

## Что не проверено

- Работа моста **с агентом `orchestrator`** (агент ещё не создан) — см. п.4 выше.
- Подключение моста к opencode через `opencode.json → mcp` (в конфиге моста пока нет — в этой
  фазе проверялся сам stdio-сервер, не интеграция в хост).
- Поведение при реальном `ORCH_TIMEOUT_MS` > часа и при обрыве stdout дочернего процесса —
  не входит в акцепты этой контрольной точки.
